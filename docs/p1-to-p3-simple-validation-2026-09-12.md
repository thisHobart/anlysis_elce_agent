从 `scripts/validate_p1_to_p3.py` 继续验证。真实山东数据上的 **P1 统计 → 点击确认 P3 → 三折回测 → 次日96点预测 → 研究包** 已完成，但连续对话、交互门禁和桌面恢复存在问题，不能据此认定完整产品流程验收通过。

P2 新闻链路尚未接入桌面，因此本次不包含 P2。P1 与 P3 共用会话数据，并记录运行父子关系；当前 P3 使用固定算法和字段，没有把 P1 的分析结论转成特征或模型选择。

使用项目配置的真实模型 `gpt-5.6-luna`。训练仅在测试进程中缩减为2轮、最多64个样本，其他模型结构和数据门禁沿用产品代码。没有修改生产代码或写业务数据库。所有会话、快照和报告隔离在 `artifacts/acceptance/`。

首次运行因山东专用数据库配置缺失停止；用户补充 `.env` 后重新取数成功。该配置问题已解除。

## 案例与实测结果

1. 选择山东并取数。
2. 提问：“只分析山东实时电价的分布，给出均值、最低价、最高价；这是一个简单测试，不做外生变量分析。”
3. 点击方案的运行按钮，生成 P1 报告。
4. 提问：“预测山东明天实时电价”，点击“确认并开始”。
5. 生成三折回测、预测 CSV、指标和报告。
6. 追问：“这次明天电价预测的结果说明什么？请说明回测表现和限制。”
7. 用隔离会话副本检查文字确认、简短续问，以及持久化 `running` 状态后的桌面重载。

|---|---|
| P1 数据范围 | 2025-11-01 00:15 至 2026-09-12 00:00 |
| P1 有效观测 | 30,240 |
| 均值 / 最低价 / 最高价 | 306.834996 / -100 / 1500；与原始输入独立重算一致 |
| 统计单位 | 报告仍标记 `unknown`，本记录不自行推断单位 |

本次耗时：初始取数42.91秒、P1规划21.19秒、统计0.22秒、P3快照准备132.54秒、缩减训练及报告4.96秒。结果追问因误触发新预测，又花费161.76秒准备数据。

真实回测每折共同有效点仅1个，合计3个，远低于每折72点的要求。模型聚合 MAE 40.250，持续法/日前同刻基线49.614，周前同刻93.915；**这些数字不能证明预测增益**。报告正确标记了“未验证出预测增益”、基线可比点不足及折间不稳定。实际价格最后更新于当天00:00，触发超过2小时警告，未触发超过24小时拒绝线。

另用显式 `--synthetic` 模式运行简单周期案例：每天96点，`price = 300 + 50 × sin(2π × slot / 96)`，提供一个周期负荷预测变量，不提供天气。真实模型负责 P1 规划，真实统计函数和预测算法执行计算。合成回测有288个共同有效点，日/周朴素基线 MAE 都为0，缩减训练后的模型 MAE 为11.138，系统正确给出没有预测增益的提示。该案例用于检查流程，不能替代真实市场验证。

## 问题与建议

### 1. 结果追问被误判为新的预测请求（高）

步骤6应解释刚生成的预测结果，实际却重新冻结数据并生成一张待确认的预测方案，没有给出回测解释。`workspace.py::_is_forecast_request` 只检查“预测/预报”“电价/价格”“明天/未来24”等词是否同时出现，没有区分“发起预测”和“解释已有预测”。这还带来不必要的历史取数开销。

建议先根据当前会话状态区分结果解释、方案修改、批准和新预测，再进行执行分派；结果解释必须能读取当前预测的指标、警告和报告。

### 2. 文字确认会丢失待确认方案（高）

在已生成 P3 方案的副本中输入“可以开始”，`current_plan` 立即被置空，分派的是 `dialogue` 而非 `forecast_execute`。本项截获桌面分派，没有额外调用模型或启动训练。点击按钮的路径能够执行。

根因位置：`workspace.py::submit_question` 对所有未命中预测关键词的消息先清除 forecast 计划。图中的 `route_main` 又把 `new_forecast_plan/execute_forecast_plan` 送到 `reply`，尚未形成完整的预测命令执行路径。

建议文字确认与按钮共用计划身份、快照指纹和批准校验；普通解释或确认消息不应清除当前方案。

### 3. 运行中重载后形成“假运行”状态（高）

将有效预测方案保存为 `status=running`、卡片状态 `running`，再新建窗口载入，得到 `status=running`、`is_busy=false`、卡片“执行中”、确认按钮隐藏。用户无法从卡片继续。

这是持久化状态重载复现，没有真正杀进程。它与算法服务能否复用折间 checkpoint 是两层问题：服务侧恢复测试通过，桌面侧没有把无后台任务的旧 running 状态转换成可重新确认状态。

建议在会话恢复时识别中断任务，显示“上次运行已中断”，提供明确的重新确认入口，并复用已完成折。

### 4. P1 完成的描述统计被判成未验证假设（中）

真实案例的报告已经包含准确的均值、最低价和最高价，但“电价总体均值、最低价和最高价可以由有效目标观测计算”被判定为没有对应确定性函数，最终停在 `result_limitations`。合成案例也复现。

位置：`planning/compiler.py::_agenda_hypotheses` 将模型提出的表述列入未验证假设；`evaluation/eda.py` 将其转成 `not_tested / needs_restatement`。

建议将用户要求的描述性统计作为可交付结果检查，避免强行转成研究假设；存在对应分布统计结果时应能完成这类简单任务。

### 5. P1/P3 的交互状态和证据混用（中）

P3 方案等待确认和运行完成时，桌面仍保留 P1 的 `result_limitations` 门禁。转入 P3 会删除原 P1 图并将旧方案标记 `stale`；P1 的 `latest_eda_summary/latest_evaluation` 却保留着。

直接检查 `_legacy_graph_import` 可见，导入状态的 `latest_run` 指向 P3 报告，但 `evaluation` 仍是 P1 的描述统计评估。结果追问新建方案后，导入的 `plan_id` 还可能对应新方案，而 `run_id/report_path` 对应上次运行。本项确认了导入对象混用，**没有声称已观察到模型基于它编造解释**。

建议分别保存 EDA 和 forecast 的当前结果，按运行身份导入同一轮证据；切换任务类型时清理旧交互门禁，同时保留历史运行记录。

### 6. 简短续问不能直接进入预测流程（中）

在 P1 结果后输入“预测山东未来24小时”，因省略“电价/价格”而未命中关键词分支，桌面实际分派 `dialogue`。本项只验证了分派；不能将它写成已完成的真实模型执行失败。

建议结合已选择的地区和电价会话主题识别省略表达，并贯通图内的 forecast 意图与执行流程。

### 7. 预测质量验收仍受真实历史版本限制（数据限制）

三折只有3个共同有效点，与此前 P3 集成记录中的限制一致。当前取数按历史锚点的可见时间截断，不能用事后价格版本补齐基线来宣称通过。后续需核实源表 `create_time/available_at` 语义和历史版本覆盖，再用完整训练配置评估预测效果。
