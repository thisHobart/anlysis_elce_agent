## 摘要（Summary）

本项目构建一个面向电价研究的本地桌面 Agent：用户用自然语言提出研究问题，系统根据本地数据和版本化 Skill 生成结构化分析方案，经用户确认后，调用白名单内的确定性统计函数完成分析，使用确定性评估器检查证据，最后生成可复现、可审计的研究报告。大模型只负责理解意图、选择研究函数、提出方案修订和解释已经产生的证据；数据加载、时间对齐、统计计算、权限判断、结果验收和状态持久化由本地代码负责。当前范围是电价与外生变量的探索性数据分析（P1）。新闻与电价结合已开始独立方案研究，预测实验仍是后续主题；无论采用何种方案，都不得绕过现有权限、溯源和人工门禁骨架。

## 动机（Motivation）

项目已经进入开发和功能迭代阶段，但开发前没有形成一份完整的 Agent 技术方案。缺少前置方案会带来几个实际问题：

- 后续开发者难以判断哪些逻辑应该放在模型、LangGraph、Skill、工具执行器或评估器中。
- 研究函数不断增加时，容易把确定性计算重新塞回提示词或自由代码，破坏可复现性。
- 方案审批、自动修订、断点恢复和结果追问等状态语义容易被局部实现改变。
- 新闻和预测阶段会引入时间可获得性、样本外验证和实验记录等新问题；如果没有共同的技术骨架，后续很容易产生第二套互不兼容的流程。

本方案的预期结果是：

1. 给当前 P1 实现提供一份可复核的技术基线。
2. 为新增 Agent、Skill、研究函数和评估规则规定统一的接入方式。
3. 明确当前版本的非目标，防止把 EDA 证据误写成因果关系或正式预测能力。
4. 记录后续主题必须继承的边界，但不在本文件中提前确定 P2/P3 的开发路线和实现组件。

## 指南级说明（Guide-level explanation）

### 3.1 开发者应如何理解这个 Agent

这个系统不是“让模型自己写代码并执行”的通用数据分析 Agent，而是一个由模型驱动研究方向、由本地程序执行研究事实的受约束研究工作流。开发时应把以下概念分开：

| 概念 | 含义 | 主要实现 |
|---|---|---|
| 研究问题 | 用户希望回答的自然语言问题 | 对话消息与 `episode_goal` |
| 研究议程 | 本轮需要验证的假设集合 | `EDAPlan.hypotheses` 与协议规则 |
| 研究函数 | 一种固定的统计过程，例如平稳性检验或领先滞后扫描 | `FUNCTION_CATALOG` 与 `app/research/tools/eda` |
| Tool Call | OpenAI Function Calling 协议边界上的一次调用 | `ToolCall`、`ToolOutput`、`ToolResult` |
| Skill | 面向一个研究领域的流程说明、函数许可和证据规则 | `SKILL.md` 与研究协议 YAML |
| 方案 | 用户可审批的研究函数及其参数集合 | `EDAPlan` |
| 研究包 | 一次研究的报告、证据、输入快照和溯源信息 | `report.md`、`methods.md`、`evidence/`、`provenance/` 等 |

“研究函数”和“工具”不能混用：研究函数是领域概念，工具是模型调用协议和执行边界。新增统计能力时，先新增确定性研究函数、结果契约、版本和测试，再决定是否把它注册为模型可见工具。

### 3.2 用户看到的典型流程

例如，用户加载目标电价和风电预测数据，并提出“判断风电是否值得进入后续电价预测特征集”。一次完整运行的心智模型如下：

```text
用户问题
  ↓
主 Agent 判断：需要新研究方案
  ↓
读取数据画像、质量信息和可用 Skill
  ↓
EDA Subagent 提议：数据可用性核验、变量分布、平稳性、相关/滞后、稳定性等函数
  ↓
本地编译器补入 data_quality，并检查函数、参数、变量、版本和滞后上限
  ↓
用户确认方案或用自然语言修改
  ↓
锁定方案和授权范围，逐个执行确定性函数
  ↓
校验结果身份、版本、数据指纹、结果键和 output_hash
  ↓
评估器判断：支持、未支持、证据不足或未检验
  ↓
生成结果卡和可复现研究包，等待用户追问或开始下一轮研究
```

如果风电数据的 `availability_type` 是 `observed_only`，系统可以描述它与电价的关系，但不能把它提升为可用于预测的候选变量。这个结论来自本地协议和评估规则，而不是模型的主观判断。

### 3.3 三类 Agent/应用角色

- `MainResearchAgent` 负责当前用户回合的路由：方法讨论、新建方案、修订方案、解释结果或确认执行。
- `EDASubagent` 负责在当前 Skill 授权的函数集合中提出 EDA 方案。它不执行统计计算，也不能改变协议的权限边界。
- `ResearchCoordinator` 负责把桌面事件转换成 Graph 输入，把 Graph 快照和事件投影到连续会话界面。它不是第三个会自行决策的研究模型。

模型通过 `app/llm` 中的共享 `ModelGateway` 接入。主 Agent 和 Subagent 可以有不同提示词和结构化契约，但不各自维护模型客户端、重写重试规则或保存隐藏思考链。

### 3.4 失败、限制与用户控制

失败是研究结果的一部分，不应被静默转换为成功：

- 未配置模型或模型调用失败：停止当前研究并提示重新配置或重试。
- 方案包含未知函数、变量或非法参数：进入方案错误中断，不执行任何函数。
- 数据在方案审批后发生变化：数据指纹不匹配，要求重新生成方案。
- 工具结果缺少声明的证据字段或哈希不一致：结果校验失败，不进入最终评估。
- 证据不足但可以缩小原审批范围：评估器允许有限自动修订。
- 需要新增变量、函数、数据范围或实验预算：回到用户审批，不由自动修订越权。

方案审批有明确的人工门禁；应用关闭期间不在后台继续执行。用户可以批准、修改、拒绝、停止、重试或要求解释已有结果。

### 3.5 对现有开发者和新开发者的影响

已有代码贡献者需要把新能力放入正确的平面：模型相关逻辑进入 Agent/LLM 层，确定性统计进入工具层，流程状态进入 Graph 层，结论规则进入评估器，界面状态进入会话投影。新开发者应先阅读 Skill 协议、工具契约、计划编译器和 Graph 状态，再添加节点或提示词；不应仅通过扩大提示词来解决权限、数据质量或状态问题。

## 参考级说明（Reference-level explanation）

### 4.1 目标、范围和非目标

#### 目标

- 让本地私有数据可以在自然语言交互下完成可控的电价研究。
- 让同一份数据、同一份方案和同一版本代码可以重放并得到一致的结构化结果。
- 让每个结论可以追溯到输入指纹、研究函数、参数、版本、结果哈希和评估记录。
- 让研究流程能够在人工审批、函数失败、应用重启和结果追问后恢复。
- 在 P1 的基础上，为新闻事件和预测实验复用统一的权限、溯源和评估骨架。

#### 非目标

- 不把相关性、互信息、Granger 前置性或分组差异解释为因果关系。
- P1 不训练正式预测模型，也不产生生产调度系统所需的实时预测。
- 不在当前版本承担 Web 服务、多用户并发、远程任务调度或云端数据存储。

└───────────────┬──────────────────────┬───────────────────┘
                ▼                      ▼
┌────────────────────────┐  ┌─────────────────────────────┐

架构分层的硬约束是：

| 层 | 负责 | 不负责 |
|---|---|---|
| 桌面交互层 | 输入问题、选择文件、展示状态、接收审批 | 统计计算和研究顺序 |
| 应用协调层 | 组装服务、调用 Graph、投影会话 | 直接绕过 Graph 改写权威状态 |
| LLM 协作层 | 意图理解、函数提议、方案修订、证据解释 | 任意代码执行、统计量计算、最终判定 |
| Skill/协议层 | 领域顺序、函数许可、证据规则和停止条件 | 执行任意脚本 |
| 规划与权限层 | 计划编译、参数校验、权限和审批范围 | 自动扩大用户授权 |
| 数据与工具层 | 数据快照、对齐、质量和确定性函数 | 解释模型意图 |
| 评估与报告层 | 结构化证据评价、研究包和溯源 | 补写不存在的数值或因果结论 |

### 4.4 Agent 与模型网关契约

#### 对话路由

`DialogueDecision` 是主 Agent 的结构化输出，允许的意图为：

- `discussion`：只解释方法或现有方案；
- `new_plan`：创建新研究方案；
- `revise_plan`：按用户反馈修订方案；
- `explain_result`：解释已有结构化证据；
- `execute_plan`：用户明确确认执行现有方案。

方案修订不是自由文本补丁：`enabled_functions` 非空时代表修订后的完整函数集合；`null` 表示保持原值；`data_quality` 由本地编译器管理，不由模型直接选择。

#### 结构化方案

模型先产生 `EDAPlanDraft`，经过 `EDAPlanCompiler` 后得到可审批的 `EDAPlan`。计划至少携带：研究问题、目标、假设、Skill 名称与版本、步骤、函数版本、所选变量、参数、规划模型、数据指纹、方案修订号和来源。计划是用户批准的对象，不是模型回复中的普通文字。

#### 共享网关与 fail-closed

`ModelGateway` 提供结构化输出、文本输出和 Function Calling 三类能力，`OpenAICompatibleGateway` 是当前实现。模型网关统一完成：

- Base URL、API Key、模型名、超时和重试配置；
- DeepSeek 与自定义 OpenAI 兼容接口适配；
- 通过 `extra_body` 关闭 thinking，并在端点拒绝该参数时自动去掉后重试；
- 结构化输出按 Function Calling → JSON Schema → JSON 模式 → 提示词 JSON 降级，兼容不支持 `tool_choice` 的思考型端点；
- 检查 `reasoning_content`、reasoning block 和 `<think>...</think>`：默认策略丢弃思考内容，严格策略（`VPP_LLM_THINKING_POLICY=reject`）发现非空内容则拒绝；
- 对空回复、无效结构化输出、无效 Function Call 或模型服务错误进行结构化失败处理。

模型上下文只接收有界对话、数据画像、质量问题、方案和压缩后的结构化证据。完整 Graph 状态、完整执行轨迹和隐藏推理不作为模型记忆保存。

### 4.5 Skill、研究协议与函数许可

Skill 是领域流程的静态说明，不是可以自动执行的脚本。每个 Skill 由 `SKILL.md` 和版本化研究协议 YAML 组成，`SkillRegistry` 负责发现、加载、版本和授权函数校验。

当前内置 Skill：

| Skill | 版本 | 用途 | 授权范围 |
|---|---:|---|---:|
| `price-exogenous-eda` | `3.2.1` | 电价与外生变量联合 EDA | 数据质量、电价结构、驱动质量、关系证据和可预测性准备度 |
| `price-forecastability-audit` | `1.2.1` | 只使用目标电价判断可预测性 | 目标形态、动态、预处理建议和朴素基线 |

`price-exogenous-eda` 的协议顺序为：

1. 市场任务与预测时钟；
2. 数据质量与可获得性门禁；
3. 电价结构、状态与记忆；
4. 外生驱动质量与冗余；
5. 电价与驱动的关系证据；
6. 可预测性准备度。

协议中的不变式包括：目标与驱动的角色不能互换；`observed_only` 或 `unknown` 变量不能成为预测候选；正滞后固定表示 `feature[t-lag]` 与 `price[t]`；负价和尖峰保留；相关、互信息和 Granger 不得写成因果结论；每条假设必须有本轮函数可以判定。

外部 Skill 可以通过程序同级的 `skills/` 或 `VPP_SKILL_PATHS` 发现，但外部 Skill 不会自动执行 `scripts/`，也不能绕过工具注册表、参数契约和用户审批。

### 4.6 计划编译、权限

模型建议转为执行队列前必须经过以下门禁：

```text
EDAPlanDraft
    ↓
EDAPlanCompiler
    ├─ 函数是否存在、是否唯一、是否按协议授权
    ├─ 参数类型/范围、变量名、分段定义、max_lag 上限
    └─ 强制加入 data_quality
    ↓
ToolRegistry：函数注册和版本匹配
    ↓
ToolPolicy：当前 Skill 权限检查
    ↓
用户 approval interrupt：批准 / 修改 / 拒绝
    ↓
AuthorizationEnvelope：锁定最大授权范围
    ↓
ToolCall 队列
```

关键规则如下：

- 同一方案中每个研究函数最多出现一次，多变量、多滞后和多分段通过批量参数表达。
- 函数、参数和结果契约都带版本；方案执行时版本不匹配即拒绝，不能“尽量运行”。
- `max_lag` 的上限按数据频率换算，不能由模型凭常识猜测。
- 用户审批同时绑定方案 ID、方案指纹和审批事实；模型返回 `execute_plan` 不等同于授权。
- 评估器触发自动修订时，只能在授权信封内收缩函数、变量、滞后或分段范围；任何扩大范围的修改必须重新进入人工审批。
- 计划校验失败、函数错误和结果限制都写入 `FeedbackPacket`，而不是被转换成空结果。

### 4.7 数据层与确定性研究工具

#### 数据输入和快照

输入数据分为研究配置、目标电价、实际外生变量和预测外生变量四种角色。数据层负责：

- 读取 CSV/Parquet，识别时间列、数值列和可获得时间列；
- 解析并统一时区，保留夏令时语义；
- 按研究配置对目标与外生变量重采样、对齐并形成标准分析帧；
- 检查有效样本、覆盖率、缺口、重复时间戳、非法数值、异常和可获得性风险；
- 生成输入文件清单和 SHA-256 数据指纹；
- 规划阶段用数据指纹绑定方案，执行阶段加载并固定快照，工具执行和最终评估复用该快照。

数据质量检查不负责替用户“修好”数据。负价、尖峰和异常点默认保留并报告；只在具体方法需要连续序列时，在方法内部进行有限时间插值并报告插值比例。

#### 原子函数和调用标识

当前工具注册表包含 30 个原子研究函数，分为：

| 类别 | 内容示例 |
|---|---|
| 数据质量 | 时间轴、覆盖、缺口、重复、数值有效性和可获得性 |
| 电价结构 | 分布、持续曲线、极端值、尖峰/负价、日历、波动、平稳性、季节和记忆 |
| 外生变量质量 | 分布、IQR 异常、漂移、两两共线性、VIF、平稳性 |
| 关系证据 | Pearson、Spearman、领先滞后、分组关系、分位响应、互信息、Granger、滚动稳定性 |
| 可预测性准备度 | 方差稳定变换检查、持续法/日朴素/周朴素基线 |

一次确定性调用使用以下链路：

```text
ToolCall(call_id, work_id, step_id, name, version, arguments)
    ↓
ToolPolicy.authorize
    ↓
ToolExecutor.execute
    ↓
numpy/pandas/scipy/statsmodels 研究函数
    ↓
ToolOutput(result_key, value, output_hash)
    ↓
ToolResult(call, tool_version, data_fingerprint, timing, output_hash)
```

- `call_id` 标识某个方案步骤的一次执行实例；
- `work_id` 由数据指纹、函数版本和规范化参数稳定生成，用于自动修订和恢复时复用确定性结果；
- `output_hash` 使用统一的 `output_fingerprint` 规则计算和复核；
- 结果校验确认调用身份、结果键、工具版本、数据指纹、哈希和声明的证据字段均正确；
- 结果缓存有界，缓存命中和 checkpoint 恢复后的结果仍必须重新通过结果校验。

### 4.8 LangGraph 研究循环、持久化与恢复

桌面端每个研究会话使用一个持久化 `ResearchLoopGraph`。状态按以下层级组织：

```text
Session：长期对话与历史
└─ Episode：一个独立研究目标，独立计数和终止状态
   └─ Iteration：计划 → 执行 → 校验 → 评估
      └─ Stage attempt：规划尝试或函数调用尝试
```

主控制流为：

```text
接收问题 → 主 Agent 路由 → 创建 Episode → 解析 Skill
→ Subagent 生成计划 → 编译校验 → 用户审批 interrupt
→ 锁定计划 → 逐函数执行 → 结果校验 → 确定性评估
→ accept / revise / need_user / reject
→ 解释结果、生成报告、请求用户或终止
```

设计要点：

- `evaluated_iterations` 只在执行完成并产出独立评估后增加；规划失败、函数重试和崩溃恢复不冒充完成的研究迭代。
- 用户审批使用 `interrupt()` 与 `Command(resume=...)`；默认要求明确确认，宿主显式启用自动模式时，超时接受仍必须带内部自动超时标记。
- Graph 的 SQLite checkpoint 是权威运行状态；桌面会话文件是展示和跨 Episode 历史投影；有限 `messages` 只是模型上下文，三者不合并。
- 应用重启后恢复未完成节点；已提交且校验通过的函数结果复用，未提交的调用才允许重跑。
- Graph schema 版本和迁移逻辑负责旧 checkpoint 兼容；不兼容状态先备份，再安全投影或重建。
- 事件由 `narration.py` 翻译为“准备、解析、规划、审批、执行、评估、报告”等中文过程说明。界面展示的是已经发生的可审计事件，不是模型私有思考链。
- 当同一规划失败、证据或议程反复出现时停止自动循环，避免 A→B→A 振荡。

默认安全预算为：单个 Iteration 最多 3 次规划尝试；单个函数调用最多 2 次尝试；一个 Episode 最多 4 次已评估 Iteration。安全预算用于防止异常无限循环，不替代正常的证据收敛和人工终止规则。

### 4.9 确定性评估与研究报告

评估器 `app/research/evaluation/eda.py` 只读取结构化工具证据和数据质量结果，不让模型直接决定结论。`AgentEvaluation` 的决策为：

| 决策 | 含义 | 后续动作 |
|---|---|---|
| `accept` | 当前议程已得到足够证据或明确限制 | 解释结果并生成研究包 |
| `revise` | 存在可在原授权范围内修复的问题 | 自动收缩方案后重新执行 |
| `need_user` | 需要补数据、补元数据或扩大授权 | 进入用户中断 |
| `reject` | 当前方案不能可靠支持目标 | 保留失败/限制并等待用户处理 |

假设状态区分 `candidate_support`、`not_supported`、`inconclusive` 和 `not_tested`，不把“没有证据”误写为“假设不成立”。评估阈值集中在 `evaluation/criteria.py`，包括季节强度、日历结构、分布形态、波动分阶段、驱动覆盖和长期漂移等规则。

一次研究包通常包含：

```text
agent-<timestamp>-<fingerprint>/
├── report.md
├── methods.md
├── figures/*.svg
├── evidence/
│   ├── data_quality.json
│   ├── eda_summary.json
│   └── agent_evaluation.json
├── provenance/
│   ├── conversation.json
│   ├── research_plan.json
│   ├── execution_trace.json
│   ├── research_loop.json
│   └── study_context.json
├── data/aligned_data.parquet
└── manifest.json
```

研究报告正文讲结论、证据和限制；方法、参数、判据、指纹和执行轨迹放在可展开或独立的复核区域，保证报告既可阅读又可审计。

### 4.10 代码组织与新增能力接入规范

| 模块 | 责任 |
|---|---|
| `app/desktop` | PySide6 启动、窗口、会话、工作区、模型配置和界面投影 |
| `app/llm` | 唯一模型网关、OpenAI 兼容接入、结构化输出和 thinking 防护 |
| `app/research/agent` | 主 Agent、EDA Subagent、对话契约和证据上下文压缩 |
| `app/research/graph` | Graph 状态、节点、路由、中断、checkpoint、迁移和过程叙述 |
| `app/research/skills` | Skill 发现、加载、版本、研究协议和授权函数 |
| `app/research/planning` | 模型草案到可执行计划的编译和约束校验 |
| `app/research/data` | 数据加载、推断、对齐、质量、快照和指纹 |
| `app/research/tools` | Tool 契约、注册表、策略、执行器和 EDA 函数 |
| `app/research/evaluation` | 结构化证据评价、反馈和后续建议 |
| `app/research/reporting` | 报告、图表、研究包和 manifest |
| `app/research/schemas` | 研究配置、质量、结果和反馈契约 |

新增能力必须按以下顺序接入：

1. 明确研究问题、输入角色和可验证假设。
2. 在领域协议中定义阶段、函数授权、不变式和停止条件。
3. 定义 Pydantic 参数/结果契约、函数版本和证据字段。
4. 将函数加入注册表、权限策略、编译器和最小测试集。
5. 为评估器增加确定性判据和限制语义。
6. 为报告和溯源补齐方法、结果和 provenance 字段。
7. 最后再把函数暴露给模型，并验证模型失败、人工审批、恢复和旧状态迁移。

### 4.11 当前阶段与后续研究边界

#### P1：电价与外生变量 EDA（当前）

已实现技术骨架包括桌面连续会话、共享模型网关、Skill/协议、计划编译、30 个确定性函数、审批中断、结果评估、研究包和 SQLite checkpoint。P1 的正式出口还需要完成真实模型、真实数据、重启恢复、桌面报告阅读器和两种 Windows EXE 的端到端验收，并补齐市场、单位、目标定义和预测可获得性元数据门禁。

#### P2：新闻与电价结合（独立研究实现，尚未产品化）

新闻采集由外部 API 负责，生产环境分析已经收集好的新闻；当前外部接口仅为占位符。独立 P2 模块已跑通规范化、模型结构化抽取边界、转载与更正去重、`as_of` 回放、统一市场时钟下的三条时间轴、事件—电价窗口分析和逐字证据包，并建立真实来源开发集与保留集。schema/Prompt `1.3.0` 已区分区域原文与市场标签、泛称与具体资产，并确定性拆分明确组合资产。尚未完成的是真实模型严格准入、外部 API 适配器和产品流程接入。当前进展见 [P2 进展状态](./phase2-status.md)，目标和门禁见 [P2 新闻事件与电价分析技术方案](./phase2-news-price-analysis-proposal.md)。

#### P3：电价预测实验（未来研究主题）

正式预测能力不在当前范围。未来若进入预测实验，必须先定义防时间泄漏、样本外比较、随机性控制和测试集治理规则；具体实验契约、模型范围、阶段顺序和交付方式另行评审。

P2/P3 标签只用于区分研究主题，不表示功能已经实现或交付日期已经确定。后续能力原则上复用模型网关、权限、人工门禁、溯源、checkpoint 和报告骨架；如需改变这些边界，必须形成新的架构决策。

## 缺点（Drawbacks）

- 方案编译、权限、审批、结果校验和报告留痕使系统明显比单次 LLM 调用复杂，新增一个函数需要修改多个契约或测试位置。
- 依赖外部 OpenAI 兼容模型接口；模型不可用时不能用本地关键词规划静默兜底。
- LangGraph checkpoint 和 Pydantic schema 演进需要迁移和兼容测试，旧会话不能简单当作临时缓存删除。
- 单机桌面应用受本机 CPU、内存和文件系统权限限制，不适合当前阶段的高并发或大规模实验调度。
- 评估器的确定性规则会牺牲部分开放式探索能力；没有对应研究函数的好问题必须先转化为可检验假设，或明确记录为超出当前能力。
- 未来引入非结构化新闻后，输入语义和抽取过程可能不完全确定；控制方式需在 P2 方案研究中明确，不能把模型输出直接当作统计事实。

## 设计理由与替代方案（Rationale and alternatives）

### 6.1 为什么采用“模型提议 + 本地确定性执行”

这是可复现性和灵活性的折中：模型擅长理解自然语言和组织研究方向，本地函数擅长稳定计算和验证。若让模型生成完整分析代码，结果会受提示词、模型版本和运行环境影响，无法可靠比较，也难以确认它是否读取了不应读取的数据。

### 6.2 为什么不用自由文本解析或只靠提示词

自由文本很难稳定区分函数名、参数和变量，提示词也不能提供真正的权限边界。Function Calling、Pydantic 契约和本地编译器共同形成可测试的拒绝路径；提示词只负责告诉模型可用能力和研究语义，不能代替门禁。

### 6.3 为什么不采用单一通用 Agent

单一 Agent 容易同时承担意图识别、规划、执行、评估和报告，导致“模型说执行了”与“本地确实执行了”混为一谈。本方案将主 Agent、EDA Subagent、确定性执行器和评估器分开，使每个部件有明确输入输出和测试边界；LangGraph 只编排它们，不承载统计算法。

### 6.4 为什么使用 Skill + 研究协议

只把工具列表暴露给模型，模型仍可能跳过数据门禁、改变研究顺序或把描述性证据写成预测结论。版本化 Skill/协议把领域知识、函数许可、顺序、不变式和停止条件从提示词中抽出，能够在本地校验、版本化和复用。

### 6.5 为什么采用 LangGraph + SQLite checkpoint

研究流程存在审批暂停、逐函数执行、自动修订、用户追问、异常恢复和应用重启等状态变化。自研状态机可以降低早期依赖，但需要自行实现中断、恢复、状态持久化和节点幂等；LangGraph 已提供适合这类状态图的运行时抽象，SQLite 则符合本地单机、无需额外服务的部署约束。其代价是需要维护 Graph schema 和迁移逻辑。

### 6.6 为什么选择本地桌面应用

数据是用户私有的电价和外生变量文件，当前主要使用方式是单人研究和人工审批。PySide6 + PyInstaller 可以在不部署服务端的前提下提供连续会话、可视化过程和 Windows 交付。若未来需要多人协作、集中数据治理或远程调度，应另立 Web/服务化架构方案，而不是在当前桌面层隐式堆叠。

## 先例（Prior art）

本方案吸收了几类成熟实践，但根据电价研究和本地交付约束做了收缩：

- **ReAct/工具调用型 Agent**：借鉴“模型提出动作、工具返回结果”的交互边界，但本方案不允许模型直接拥有任意工具；工具集合由 Skill、注册表、编译器和用户授权共同收缩。
- **结构化输出与类型契约**：借鉴 JSON Schema、Function Calling 和 Pydantic 的契约化思想，把模型输出、参数和结果从文本变成可拒绝、可测试的对象。
- **LangGraph 等状态图运行时**：借鉴节点、边、中断、恢复和 checkpoint 模型，把研究工作流表示成显式状态，而不是依赖一段不断增长的对话历史。
- **实验追踪系统**：借鉴实验规格、输入版本、参数、指标和失败结果需要一起保存的原则；当前先用研究包、数据指纹和 manifest 实现单机版本，不预设远程实验平台。
- **数据分析和统计软件的审计习惯**：借鉴方法说明、参数记录、结果表和可复核图表的组织方式；报告同时提供可读正文和机器可读证据。

这些先例只说明可复用的工程经验，不替代本项目的领域协议。电价数据的负价、尖峰、季节性、时区、预测发布时间和可获得性仍必须由本地研究规则明确表达。

## 未决问题（Unresolved questions）

以下问题需要在对应阶段开工前确认，当前不应通过代码默认值掩盖：

1. 真实默认模型供应商的选择依据是什么：成本、Function Calling 稳定性、延迟还是数据合规？
2. 是否需要保留并统一 `VPP_LLM_ENABLED` 开关，还是完全以 Base URL 和模型名判定模型可用性？
3. 当前 P1 的市场名称、价格单位、目标定义、预测起点和预测范围由谁提供，哪些字段必须变成硬门禁？
4. 外部 Skill 的版本信任、审核、签名或目录管理规则是什么？
5. P2 面向哪个市场、时间范围和业务问题，事件关联证据是否作为首个正式出口？
6. 外部新闻 API 的样例契约、稳定 ID、许可、采集延迟、本地保存周期和可追溯标识是什么？
7. 新闻时间语义、事件定义、抽取质量、人工复核和统计验收分别采用什么口径？
8. P2 应复用还是重构当前 `StudyConfig`、`EDAPlan`、工具目录、评估器和研究包接口？
9. P3 的实验契约与现有 `EDAPlan` 是包含关系、并列关系还是统一抽象？
10. P3 默认滚动切分的训练窗口、验证窗口、折数、预算和随机种子如何定义？
11. 是否排除需要 GPU 或联网下载权重的深度时序模型？
12. 测试集独立解锁需要哪一级用户确认，解锁次数和测试集结果如何防止重复使用？
13. 研究包和未来索引的清理、归档和备份策略是什么？
14. 真实模型、真实数据、桌面重启和 onedir/onefile EXE 的最终验收负责人及通过阈值是什么？

P2 可以在独立草案的门禁内开展合成夹具与确定性测试，但未确认部分不得写成已批准的生产行为；P3 仍不得在当前文档中预设开发路线。
