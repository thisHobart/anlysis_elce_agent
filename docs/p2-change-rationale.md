# P2 新闻数据处理改造说明

## 1. 文档目的

本文解释 P2 新闻数据处理阶段为什么要进行本轮改造，以及每项改造解决了什么问题。

P2 的 MVP 不是“让模型直接预测电价”，而是把新闻变成一套可以复核、可以按历史时点回放、可以与价格数据对齐的事件证据。改造的判断标准因此是：

1. 新闻事实不能被静默丢失或凭空补全；
2. 后续版本不能改写过去已经可见的状态；
3. 价格分析不能把不完整窗口、并发事件或未来信息包装成可靠结论；
4. 每条结果都能回到原文、版本、时间和处理方法；
5. 系统要支持批处理失败隔离、人工复核和可恢复运行。

## 2. 改造前的主要问题

原流程已经具备规范化、事件合并、时间对齐、价格分析和证据包等基础能力，但仍存在几类会影响 MVP 可信度的问题。

| 原问题 | 直接风险 | 影响的产品结果 |
|---|---|---|
| 明确撤回的容量可能被旧版本重新填回 | 历史状态被错误恢复 | 事件台账、特征表和报告不一致 |
| 价格窗口只要有少量数据就可能计算 | 24 小时窗口可能只有几个区间 | p 值、偏离值和结论不可靠 |
| 对照窗口没有严格匹配和去重 | 日历效应或重叠样本被误当成事件效应 | 事件—价格关联被高估 |
| 并发事件没有强制标记 | 同一价格变化可能被多个新闻重复归因 | 事件解释过度 |
| 日期级新闻只能整体隔离 | 可靠事件事实被丢弃 | 新闻台账召回率下降 |
| 一条坏 JSON 行可以中断整批导入 | 少量脏数据拖垮整个任务 | 批处理不可用 |
| 模型技术失败可能进入缓存 | 下一次运行继续复用失败结果 | 问题无法自动恢复 |
| 人工复核没有持久化版本 | 复核决定无法审计或重放 | 不能形成稳定工作流 |
| 重复基准只看最后一轮 | 前几轮失败可能被最后一次成功掩盖 | 模型资格判定过于乐观 |

这些问题的共同点是：它们不一定立即抛出程序异常，很多会产生“看起来正常、实际上不可信”的结果。因此本轮改造优先处理数据血缘、时间可得性和失败隔离，而不是继续堆叠新闻关键词。

## 3. 事件契约为什么要扩展

修改位置：[contracts.py](../app/research/news/contracts.py)

### 3.1 将事实可信度和分析资格分开

一条新闻可能可靠地说明“某机组在 5 月 24 日停运”，但没有精确到小时的生效时间。它可以进入事件台账和人工复核，却不能直接进入 30 分钟价格窗口。

因此事件现在分别记录：

- `analysis_eligibility`：是否具备精确价格分析资格；
- `time_resolution`：时间只有日期、小时、区间还是精确时刻；
- `effective_start_at`：只有通过时间门禁时才填写。

这样改是为了避免在“提高召回率”和“保持时间分析严谨”之间二选一。事实先保留，统计资格单独控制。

### 3.2 保存复核状态和置信度

事件现在可以处于 `unreviewed`、`accepted`、`corrected` 或 `rejected` 状态，并保存模型候选置信度。

置信度只用于排序和门禁，不直接当成正确概率。这样人工复核可以处理高风险候选，同时不会把模型自报分数误认为统计保证。

### 3.3 保存坏输入记录

新增 `NewsInputIssue`，记录行号、文件路径、原始行和失败原因。输入错误因此成为可审计结果，而不是只出现在终端日志中。

## 4. 为什么要修改实体解析和模型抽取

修改位置：[model_extraction.py](../app/research/news/model_extraction.py)、[entity_resolution.py](../app/research/news/entity_resolution.py)

### 4.1 原文名称和规范化身份要分开

同一个区域可能写成“辽宁”“辽宁电网”或英文缩写；同一个资产也可能出现简称、全称或机组组合描述。如果直接用模型原文作为事件身份，会出现同一事件被拆成多个事件，或者不同资产被错误合并。

现在同时保存：

- 原文提及和字符位置；
- 规范化后的区域、资产、市场和资产组键；
- 原文字段和规范化身份的对应关系。

这样做的目的，是让“证据保留原文”和“事件合并使用稳定身份”各自承担合适的职责。

### 4.2 多事件新闻必须候选级隔离

一篇新闻可能同时包含两个事件，其中一个候选有效、另一个候选缺少时间或证据。过去如果按整篇新闻失败，合法事件也会被一起丢弃。

现在一个候选失败只进入 `candidate_quarantines`，其他合法候选继续进入事件表。这样可以提高真实新闻的有效召回，同时保留失败候选供人工复核。

### 4.3 模糊时间保留事实，但不制造时间

“今日凌晨”“本周末”“5 月 24 日”不能自动变成一个具体结算时刻。自动补成午夜或某个小时会制造前视信息和伪精确数据。

现在的处理是：

- 原文时间短语仍然保存；
- 记录时间精度；
- 没有精确时刻时标记为 `needs_time_review`；
- 不进入需要精确零点的价格窗口。

这满足了两个目标：新闻事实不静默丢失，价格统计不使用虚构时间。

### 4.4 模型技术错误不能当成正常隔离

模型不可用、协议错误和结构化输出失败与“新闻确实不适合分析”是两种不同情况。前者需要重试或修复配置，后者才是业务隔离。

因此技术错误不会进入可复用缓存，并保留每次尝试记录。否则系统可能在重启后继续复用一次暂时失败的结果。

## 5. 为什么要修改事件版本合并

修改位置：[merging.py](../app/research/news/merging.py)、[versioning.py](../app/research/news/versioning.py)

### 5.1 撤回字段必须是持续状态

假设新闻版本如下：

| 版本 | 内容 | 正确状态 |
|---|---|---:|
| 10:00 | 不可用容量 500 MW | 500 MW |
| 12:00 | 明确撤回容量 | 未知 |
| 13:00 | 只重复停运事实，没有容量 | 仍然未知 |
| 15:00 | 明确给出 350 MW | 350 MW |

如果 13:00 版本还能从更早版本补回 500 MW，历史状态就被破坏了。现在 `cleared_fields` 作为持续的撤回标记，只有新的明确赋值才能结束撤回状态。

### 5.2 `as_of` 必须反映当时真正能看到的版本

事件分析需要回答两个不同问题：

- 今天回看，最终事件状态是什么；
- 当时市场能够知道什么。

因此版本库保留全部版本，按 `as_of` 重建历史视图。后来的更正可以改变更正之后的视图，但不能改写更正之前已经生成的特征。

## 6. 为什么价格分析升级到 2.0

修改位置：[analysis.py](../app/research/news/analysis.py)

### 6.1 不完整窗口不能冒充完整窗口

一个标记为 `[0,24h]` 的窗口，按 30 分钟市场时钟应有 48 个价格区间。如果价格范围只剩 2 个区间，均值和波动仍然可以算出来，但不应该被描述为 24 小时事件结果。

现在窗口必须满足：

- 窗口长度是结算间隔的整数倍；
- 实际价格区间数等于理论区间数；
- 样本数达到最低要求。

### 6.2 对照窗口要与事件窗口可比较

价格有明显的小时、工作日和周末规律。简单地把所有无事件区间混在一起，会把日历差异带入事件效果。

现在对照窗口按以下条件匹配：

- 同一时刻；
- 工作日/周末类型一致，或同一星期几；
- 窗口完整；
- 对照窗口之间不能重叠。

此外，系统保存实际使用的对照窗口，便于审计和复现。

### 6.3 不通过重复抽样制造样本量

原实现可能从较小的对照池中重复抽样。重复抽样可以增加计算次数，却不能增加独立信息量。

现在使用全部合格对照窗口计算经验尾部比例，并在结果中明确标记为经验对照方法。这样统计结论会更保守，但不会因为伪造的样本量而显得过度显著。

### 6.4 并发事件只能作为混杂因素处理

如果停运、高温和输电限制同时落在一个价格窗口内，价格变化不能直接归因给某一个事件。系统现在保留窗口描述统计，但将并发事件写入 `confounding_event_ids`，并限制单事件结论。

这符合 MVP 的定位：先提供可解释证据，避免把相关关系误写成单事件因果效果。

## 7. 为什么要增加提前公告特征

修改位置：[features.py](../app/research/news/features.py)

新闻的预测价值可能在事件生效之前就产生。只记录“当前已经发生的事件”会丢掉这部分信息。

因此特征表增加：

- 新公告事件数；
- 已公告但尚未生效的事件数；
- 距最近生效时间；
- 按供给、需求、输电方向拆分的容量。

这些特征仍然按每个价格区间的可获得信息构建。公告已经可用但事件尚未生效时，事件出现在 `upcoming_event_ids`，不会提前出现在 `source_event_ids`。

## 8. 为什么要增加持久化工作台

修改位置：[workspace.py](../app/research/news/workspace.py)、[run_news_workbench.py](../scripts/run_news_workbench.py)

如果 P2 只能通过 Python 函数调用，研究结果就无法形成实际工作流。MVP 至少需要支持“导入—处理—复核—导出—重跑”。

当前工作台提供：

- JSONL 按行导入和坏行隔离；
- SQLite 保存文档、抽取缓存、尝试记录和复核审计；
- 由文档版本、模型配置、抽取器版本和市场时区组成缓存身份；
- 接受、拒绝、修正三种复核处置；
- 每次运行独立导出，不覆盖旧结果；
- `manifest.json` 保存完成状态和文件哈希。

人工修正不会覆盖历史输入，而是生成一个从复核时刻起可见的新本地版本。这样旧的 `as_of` 结果仍然可以复现。

## 9. 为什么要修改真实新闻资格测试

修改位置：[benchmark.py](../app/research/news/benchmark.py)、[benchmark_real_news_extraction.py](../scripts/benchmark_real_news_extraction.py)

一次模型运行通过，不足以证明模型稳定。模型可能在不同运行中改变事件类型、资产或处置结果。

现在资格要求：

- 所有重复运行都达到阈值；
- 每个案例的处置稳定；
- 技术失败不能计为“正确隔离”；
- 语料明确区分开发集、回归集和独立验收集；
- 独立验收集需要第二人复核。

历史保留集已经用于发现和修复实体、时间和隔离问题，因此现在标记为 `regression`。它可以防止旧问题回归，但不能继续作为完全独立的最终验收证据。

## 10. 改造后的产品效果

改造后，P2 MVP 可以稳定完成以下流程：

```text
新闻批量导入
  → 坏行隔离与规范化
  → 结构化事件抽取
  → 原文证据和实体校验
  → 事件版本合并与 as_of 回放
  → 人工复核
  → 无泄漏事件特征
  → 事件—价格描述与关联分析
  → 报告、CSV、JSON 和哈希清单
```

它能够回答：

- 发生了什么事件；
- 哪个来源、哪个版本给出了这个事实；
- 市场什么时候可以知道；
- 事件什么时候生效；
- 哪些事件已经发生、哪些只是提前公告；
- 事件附近价格是否出现与预期方向一致的时间关联；
- 当前结果是否受到样本不足、并发事件或隔离记录影响。

它还不能直接回答“新闻让价格上涨了多少”或“加入新闻后预测一定变好”。这些问题需要真实市场配置、独立测试集、时间顺序预测实验和反事实假设，属于后续阶段。

## 11. 验证结果

本轮修改后的验证结果：

- 全项目测试：581 项通过；
- Ruff 静态检查：通过；
- 工作台专项测试：16 项通过；
- 已用合成新闻和价格实际生成独立结果目录；
- 结果目录包含报告、事件台账、特征表、输入问题、复核队列和文件哈希。
