## 1. 目标与领域边界

主 Agent 从会话开始就是电价领域助手。即使底层使用通用大模型，也必须通过初始系统提示词明确其服务范围，使回答、需求理解和能力调度始终聚焦电价领域。

领域范围包括电价形成机制、电力市场、电价数据特征、电价分析与预测，以及与电价相关的负荷、新能源出力、天气、供需、政策和新闻事件。外生因素只有在服务于电价问题时才纳入讨论，不延伸为无关领域的通用问答。

“问候、概念解释、讨论想法、需求澄清”在本文中的具体含义为：

- 问候：简短回应，并自然引导至电价相关问题，不启动研究。
- 概念解释：回答电价及其相关领域的知识问题，不要求用户先提供数据。
- 讨论想法：围绕电价研究目标、分析思路、方法选择和结果理解展开讨论。
- 需求澄清：明确用户希望了解的电价问题，以及必要的市场、时间范围、数据或预测目标。
- 无关问题：简短说明当前助手专注电价领域，引导用户提出相关问题，不展开无关话题。
- 关联不明确的问题：结合上下文判断；只有关联会影响回答时才作最小必要澄清，不对每个简短追问重复确认。

领域聚焦不等于每次都进行研究。只有用户请求需要实际数据计算时才进入分析路由；上传数据、问候或询问概念本身不触发研究。

## 2. 当前实现与需求的差距

| 当前实现 | 对行为的影响 | 修改方向 |
| --- | --- | --- |
| 主 Agent 定义为只识别意图、选择路由的对话控制器 | 电价领域交流能力被压缩为工作流控制 | 将电价领域交流、理解需求与协调能力作为主职责 |
| 规划器一次返回 EDAPlanIntent.functions | 尚未获得分析结果就选择整组方法 | 提出初步方向，根据后续证据继续选择工具 |
| 编译器按领域协议重新排序 | 模型不能根据当前分析依赖组织顺序 | 只强制方法前提和真实依赖 |
| auto_recommend 注入固定筛查函数集合 | 自动选变量进入预设分析套餐 | 将筛查套餐改为有适用说明的可选配方 |
| 每个函数每计划最多一次，变量为计划级选择 | 难以比较不同变量、窗口或变换 | 每次调用独立声明数据范围和参数 |
| 自动修订只能删减批准过的函数 | 新证据难以触发追加方法 | 用任务范围、数据范围、工具范围和预算表达授权 |
| 业务主链使用结构化计划生成，独立 invoke_tool_calls 接口未接入该链路 | 缺少逐步的模型—工具反馈 | 建立原生调用、结果回传和继续决策的循环 |

当前系统并非每次执行全部固定方法：它已经允许选择部分函数，领域协议也包含调用时机说明。重构重点是解除一次性计划、全局固定排序和固定筛查对动态分析的限制。

## 3. 目标运行流程

```text
用户消息
  → 电价领域主 Agent：理解上下文、判断请求
      → 领域知识/方法交流：直接回答
      → 必要信息缺失：澄清需求
      → 无关问题：说明领域范围并引导
      → 实际电价分析请求：进入研究路由
          → 获取数据画像及已有证据
          → 提出初步分析方向
          → 在任务授权范围内选择工具
          → 校验并执行
          → 回传结果给研究 Agent
          → 继续分析 / 请求信息 / 完成回答
      → 预测等其他已实现业务：进入对应路由
```

固定的是上述运行框架。具体方法、顺序、参数和后续分支由模型根据问题、数据与工具结果选择；程序负责执行约束、数据一致性及可恢复性。

进入研究路由后仍继承电价领域边界。普通交流不清空已有研究状态，也不自动恢复暂停的计算；应依据当前请求决定是否继续。

## 4. 主 Agent 提示词与路由修改

### 4.1 初始系统提示词建议

以下文字作为主 Agent 系统提示词的角色与行为核心，须从会话首次请求开始注入，并在后续模型请求中持续保留，不依赖用户自己声明领域。

```text
你是电价领域助手，负责围绕电价问题与用户交流、理解需求，并协调已提供的专业能力。

你的讨论范围是电价形成机制、电力市场、电价数据分析与预测，以及与电价直接相关的负荷、新能源出力、天气、供需、政策和新闻事件。涉及这些外生因素时，应围绕它们与电价问题的关系展开。

对问候简短回应，并自然引导至电价相关问题。对电价领域的概念、方法、分析想法和已有结果，可以直接解释或讨论，不要求每次都开展研究。对明确无关的问题，简短说明你专注电价领域并引导用户返回相关主题，不展开无关内容。

根据当前请求与对话上下文，决定直接回答、澄清必要信息，或进入相应业务流程。只有用户要求对实际数据开展分析时才进入电价分析流程；上传数据或讨论方法不等于要求立即执行。

区分一般领域知识、分析建议和当前数据已经验证的结论。一般知识可以直接解释；当前数据的统计数值、执行状态、报告和图表必须依据已有证据。市场规则涉及具体地区和时间时应说明适用范围；缺少可靠信息时明确不确定性。

沿用对话中仍有效的目标和约束。用户改变目标时，以新的明确要求为准。只在缺失信息会影响回答或执行时提出必要问题。
```

### 4.2 代码配套

- 调整 `app/research/agent/prompts.py` 的主 Agent 提示词，保留真实证据、产物状态和执行确认约束。
- 调整 `app/research/agent/orchestrator.py` 的路由说明与契约，使领域交流、必要澄清和范围引导均可直接回复；不必为每种对话形式新增独立 Graph 节点。
- 主 Agent 可以内部使用结构化路由输出，但用户可见回答应自然，不暴露控制器字段。
- 检查桌面入口是否存在绕过主 Agent 的关键词分流，确保上传数据、提到“分析”等行为不会单独强制启动任务。
- 已有预测等业务路由继续以实际能力和当前用户意图为依据。

## 5. 研究 Agent 与动态工具循环

### 5.1 研究提示词建议

```text
你负责依据用户的电价分析目标、数据特征和已有证据组织分析。

使用提供的基础工具和可选分析配方，选择当前有助于回答问题的步骤。先了解必要的数据画像，可以提出初步分析方向，并根据工具结果调整方法、参数和执行顺序。

每次调用应具有明确用途，遵守工具适用条件和任务授权范围。不要为了覆盖方法清单执行与问题无关的分析。证据足以回答问题时结束；缺少关键条件时说明限制或请求必要信息。

数据结论必须有工具证据支持。不要把相关关系解释为因果关系，也不要把样本内结果当作样本外预测收益。
```

### 5.2 执行协议

1. 提供目标、数据画像、历史有效证据和可用工具 Schema。
2. 模型返回工具调用或完成回答；不强制每轮必须调用工具。
3. 程序检查工具权限、参数、数据范围和方法前提。
4. 执行一个调用或一组互不依赖的调用。
5. 用匹配的 provider call ID 回传每个调用的成功结果或结构化错误。
6. 模型依据返回证据继续选择方法、请求信息或结束。

`app/llm/gateway.py` 的消息契约需要支持 assistant 工具调用列表。当前工具结果消息虽有 tool_call_id，但 assistant 消息缺少对应调用列表，不能完整保存原生工具交互历史。

`invoke_tool_calls` 当前强制返回调用，需要扩展或新增响应契约，表达“工具调用”与“最终回答”。保留 provider call ID 用于模型协议，保留本地调用 ID 和 work_id 用于执行审计与复用，明确两者映射。

工具结果采用有界摘要回传，保留完整证据引用；当摘要不足以继续判断时，应允许查询所需证据细节。失败结果必须有对应调用的返回，不伪造成功。

## 6. 基础工具与可选分析配方

### 6.1 基础工具

复用现有统计 handler，按需要逐步扩展分布统计、分组汇总、滚动统计、相关分析、自相关、平稳性检验、分段比较等能力。每次调用独立指定适用的数据引用、变量、时间范围、窗口或变换参数；不同工具只暴露自己支持的字段。

每个工具说明至少包含用途、调用时机、方法前提、参数含义、输出结构和解释限制。现有领域协议中的 function_rules 可以迁移或复用为工具说明。

### 6.2 可选配方

允许提供由多个基础工具组成的分析配方，例如“电价快速画像”组合分布、日历分组和波动统计。必须注明适用场景，例如“首次整体了解一批电价数据”；用户只要求均值时不运行完整配方。

模型可以选择配方或其中的单个基础工具。固定组合展开后仍记录每项调用、参数和证据，避免隐藏计算过程。有条件分支的配方作为方法指南，由模型根据中间结果决定是否进入后续步骤。

## 7. 流程约束、状态和结果修改

- 将领域协议拆分为执行前提与方法建议。保留数据一致性、方法输入要求等必要检查，去掉对所有问题统一强制的方法顺序。
- 将 `auto_recommend` 的固定函数注入改为可选配方；变量推荐方法由任务和证据决定。
- 将“每函数最多一次”改为按数据指纹、函数版本及参数识别工作。允许不同参数下重复调用，同样的工作可复用结果。
- 将当前预先锁定的完整队列改为逐轮接收调用；独立调用可批处理，有依赖的调用等待前置结果。
- 调整依赖函数名唯一性的计划结构、授权映射、结果汇总和报告生成。不同窗口、变量或变换的结果按调用保存，不能互相覆盖。
- 保留注册表、Pydantic 参数校验、数据快照、结果哈希、结果仓库、checkpoint 和故障恢复。
- 用用户目标、允许使用的数据与工具范围、计算预算表达研究授权。初步方案说明意图和条件分支，不要求预先穷举全部方法。
- 根据用户问题与方法有效性评估完成情况，不要求无关问题也完成整个领域研究阶梯。采用预算、无新增证据和重复调用检测控制循环。

## 10. 四项缺口的最终实现

### 10.1 数据解析边界

路由前状态只包含 `study_input` 和 `has_executable_data`。`StudyInputDescriptor` 创建时只验证路径存在、后缀和基础配置，不读取表格，不推断时间列、目标列、频率或外生变量。桌面数据面板在此阶段显示“数据已选择，尚未检查”。

主 Agent 选择实际分析后，`resolve_study_context` 才调用数据推断逻辑；生成的 `StudyConfig` 在 checkpoint 中冻结并供后续审批、修订和执行复用。`discussion`、结果解释、问候、概念/方法讨论、澄清、新闻移交均绕过解析节点。预测仍先进行业务路由，是否读取源数据由预测处理器决定。

### 10.2 权威调用证据

`CallEvidenceLedger` 按执行顺序校验 `call_id`、`provider_call_id`、`work_id`、函数版本、规范化参数、数据指纹、结果引用、结果哈希、状态和结构化错误，并提供按调用和函数查询能力。

评估、报告和图表的公开接口只接受 Ledger，不接受兼容摘要。消费者使用的分析视图由 Ledger 在内存中即时派生；不会读取 `eda_summary.json`。研究包先写入 `evidence/call_evidence.json`，随后才生成兼容投影。失败和取消调用进入“执行记录与限制”，不参与数值结论。最终 `EDAPlan` 仍只列出成功或复用的原子调用，作为可复现执行清单。

### 10.3 Provider 消息闭环

每个模型工具回合按以下顺序处理：

1. 校验所有 provider call ID 非空、回合内唯一且未被历史回合使用。
2. 整回合合法后，原子写入 assistant tool calls 和对应 `ToolCallGroupRecord`。
3. 编译错误只关闭对应 ID；同批次其他独立调用继续执行。
4. 可恢复执行错误关闭所属 ID；配方内尚未执行的子调用标记为 `cancelled_due_to_batch_abort`。
5. 权限、数据指纹等致命错误先关闭失败 ID，并为其余 ID 写入取消结果，再进入用户中断。
6. checkpoint 可以保存唯一 pending group；恢复后继续该批次。再次调用模型和最终评估前必须全部严格闭合。

相同 `work_id` 复用结果时不重复计算，也不增加实际调用计数。配方的多个原子结果继续聚合成与一个 provider call ID 对应的一条 tool 消息。

### 10.4 验收矩阵

默认 CI 在 Windows 环境执行 Ruff、编译检查和全部离线测试。真实协议工作流分为三个独立任务：

```powershell
python scripts/probe_dynamic_tool_turn.py --case openai-native --output artifacts/live/openai-native.json
python scripts/probe_dynamic_tool_turn.py --case gemini-native --output artifacts/live/gemini-native.json
python scripts/probe_dynamic_tool_turn.py --case prompt-json --output artifacts/live/prompt-json.json
```

每个探针执行“模型提出工具调用 → 使用相同 call ID 回传本地模拟结果 → 模型输出无工具调用的完成正文”两轮交互。输出只保留 provider、模型名、结构化模式、finish reason、调用名称、ID 和参数键等脱敏元数据，不保存密钥、授权头、完整提示词或模型正文。

`.github/workflows/function-calling-live.yml` 支持手动、定时及 release gate 调用；三个真实案例必须全部通过，缺少凭据视为该工作流配置失败。普通 PR 只运行三类适配器的离线模拟，不因没有外部凭据而阻塞。
