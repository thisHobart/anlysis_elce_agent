## 1. 方案总览

本系统需要在模型输出不可控、不可复现的前提下，产出可复现、可审计的研究结论。全部技术选型均由这一矛盾派生。

| # | 要达成的目的 | 技术挑战 | 采用的技术与机制 | 阶段 |
|---:|---|---|---|---|
| 1 | 自然语言问题转为可执行的分析计划 | 模型输出格式不稳定，可能夹带推理文本与虚构参数 | Function Calling 强制结构化输出，配合计划编译与 fail-closed 校验 | P1 |
| 2 | 分析计算可复现、可重放 | 模型生成的分析代码无法版本比对与审计 | 白名单原子函数注册表与确定性执行器，基于 numpy / pandas / scipy / statsmodels | P1 |
| 3 | 领域研究遵循固定证据顺序 | 提示词约束可被后续对话稀释或绕过 | 版本化 YAML 研究协议与本地授权函数集，构成 Skill | P1 |
| 4 | 支持人工审批中断与崩溃恢复 | 长流程状态易丢失，审批点需要可暂停可续跑 | LangGraph 的 interrupt / resume 与 SQLite checkpoint | P1 |
| 5 | 结论判定不依赖模型主观评价 | 模型自评不稳定，随版本漂移 | 基于结构化证据的确定性评估器，输出四态决策 | P1 |
| 6 | 全链路溯源与防陈旧执行 | 数据、代码、参数在流程中可能漂移 | 数据指纹、计划版本、工具版本、结果哈希与 manifest | P1 |
| 7 | 私有数据零部署使用 | 数据不得离开本地，用户无运维能力 | PySide6 桌面应用与 PyInstaller 打包 | P1 |

## 3. 第一阶段技术议题详述

### 3.1 自然语言问题转为可执行分析计划

**目的**　用户以自然语言提出研究问题，系统须将其转换为参数完整、变量合法、可直接执行的分析计划，且转换过程的失败必须显式暴露而非静默降级。

**方案**　由 `MainResearchAgent`（`app/research/agent/orchestrator.py`）判断当前回合属于方法讨论、新建方案、修订方案、结果解释还是执行确认，`EDASubagent`（`app/research/agent/subagents/eda.py`）在当前 Skill 授权范围内选择具体函数并形成结构化计划。结构化计划固定使用 Function Calling 产出，不接受自由文本解析。

**机制**　模型接入集中于 `app/llm`：`ModelGateway`（`gateway.py`）定义 Agent 自有的类型化消息、结构化输出、文本输出与 Function Calling 契约，`ResearchModelGateway`（`openai_compatible.py`）把这些对象交给显式选择的 Chat Completions 或 Responses 适配器，`factory.py` 为主 Agent 与 EDA Subagent 注入同一网关。`tools`、`tool_choice`、消息角色和结构化 schema 属于核心协议，端点拒绝或未返回原生调用时直接报告配置不兼容，不再切换 API，也不解析自由文本或提示词 JSON。`compat.py` 只允许移除温度、Provider 自动添加的推理控制和 `parallel_tool_calls` 等非核心字段，并保留非标准 HTTP 响应信封修复。端点仍返回 `reasoning_content`、reasoning block 或 `<think>` 内容时，默认策略（`VPP_LLM_THINKING_POLICY=strip`）丢弃思考内容后继续，严格策略（`reject`）维持 fail-closed。模型返回无效调用、空回复或未授权内容时流程暂停并提示重试。

**选型理由** 〔待确认〕　候选方案 A 为提示词约定 JSON 格式并由正则或 JSON 解析器提取，实现成本低，但格式违约率随对话轮次上升，且无法区分模型意图错误与格式错误；候选方案 B 为自定义 DSL，须自行实现解析、校验与错误提示，成本高于直接复用 Function Calling 的参数 schema。选择 Function Calling 的关键收益在于参数 schema 由服务端参与约束，违约在调用侧即被捕获。关闭 thinking 是以推理质量换取输出稳定性与延迟可控的取舍，其前提是复杂判断已由确定性组件承担，模型不需承担长链推理。

**代价与边界**　方案质量受模型对 Skill 描述与参数 schema 的理解能力限制，更换模型供应商或 API 形式须重新验证消息角色、结构化输出与 Function Calling 兼容性。自动化测试只能覆盖本地边界行为，真实端点能力仍须独立验收。

### 3.2 保证分析计算可复现与可审计

**目的**　同一数据与同一计划两次执行须产出完全一致的结果，且任一数值均可回溯至确定的函数版本与参数。

**方案**　建立包含 30 个原子研究函数的工具注册表，按数据可用性核验、电价自身规律、外生变量质量、关系证据、可预测性准备度五类组织，全部基于 numpy、pandas、scipy 与 statsmodels 实现。模型只能选择函数与参数，不能提供实现。

**机制**　函数名的单一事实来源是 `app/research/tools/catalog.py` 中的 `ResearchFunctionName` 字面量联合类型；实现按主题分布于 `app/research/tools/eda/` 的 `price.py`、`exogenous.py`、`relationships.py`、`dependence.py`、`drivers.py`、`segments.py`、`structure.py` 等文件。工具执行链如下。

```text
模型 Function Call
→ EDAPlan
→ Planning Compiler (planning/compiler.py)
→ ToolRegistry (tools/registry.py)
→ ToolPolicy (tools/policy.py)
→ ToolExecutor (tools/executor.py)
→ numpy / pandas / scipy / statsmodels 确定性函数
→ ToolResult
```

关键约束包括工具名须命中注册表且版本精确匹配，变量名须来自当前研究配置，目标序列不能冒充外生变量，每个函数在一个计划中最多出现一次而多变量多滞后多分段通过批量参数表达，`data_quality` 由编译器强制加入，模型不能提供函数路径、任意 Python、SQL 或未注册参数。负价与尖峰作为市场现象保留，不做静默删除或截尾。相关性、互信息、Granger 前置性与分组差异仅作为描述性证据，不自动等同于因果或样本外预测增益。

**选型理由** 〔待确认〕　候选方案 A 为沙箱 Python 解释器，表达力最强，但生成代码不可复现、不可版本比对，审计时须逐段阅读模型代码，与可复现性优先的质量目标直接冲突；候选方案 B 为受限 DSL，仍须自研解析与安全校验，且用户与审计者需要学习额外语法。固化原子函数库把安全边界从运行时前移至注册时，使越权在编译阶段即被拒绝，是三者中审计成本最低的方案。

**代价与边界**　新增分析能力必须先扩充函数库，模型无法即兴组合，函数库覆盖度成为产品迭代速度的瓶颈。未来如果出现远大于 EDA 的组合空间，是否上移计划抽象层级需要单独评审，不能直接放宽注册和权限边界。此外，`catalog.py` 以字面量联合类型枚举函数名，在引入下一研究领域前需要检查它是否仍适合作为单一事实来源。

### 3.3 约束领域研究顺序而不依赖提示词

**目的**　电价研究存在客观的证据先后顺序，数据可用性核验未通过时不应进入关系分析。该顺序须由系统强制，不能因对话轮次增加而被稀释。

**方案**　将研究顺序、阶段目标、授权函数集合、函数规则与退出门槛写入版本化 YAML 研究协议，与 `SKILL.md` 共同构成 Skill。当前内置两个 Skill，Skill 与协议各自独立版本化。

| Skill | Skill 版本 | 协议 ID | 协议版本 | 授权函数数 | 适用范围 |
|---|---|---|---|---:|---|
| `price-exogenous-eda` | 3.2.1 | `electricity-price-evidence-ladder` | 2.2.1 | 30 | 电价与外生变量联合 EDA |
| `price-forecastability-audit` | 1.2.1 | `price-forecastability-ladder` | 1.2.1 | 14 | 仅有目标电价，或先判断电价自身可预测性 |

**机制**　`price-exogenous-eda` 的六层证据阶梯为：市场任务与预测时钟 → 数据质量与可获得性门禁 → 电价结构状态与记忆 → 驱动变量质量 → 关系稳定性 → 可预测性准备度。协议以三个字段承载约束：`invariants` 是任何计划都不得违反的不变式（如「正滞后固定表示 `feature[t-lag]` 与 `price[t]`」「目标与驱动平稳性 verdict 同为 unit_root 时同期相关按伪相关处理」），`stop_conditions` 是须停止而非降级的条件，`stages` 是分层的函数授权与退出门槛。模型只在协议授权集合内选择函数，不能通过提示词改变本地权限。外部 Skill 可经程序同级 `skills/` 目录或 `VPP_SKILL_PATHS` 加载，但不能注册新函数或执行任意脚本。

协议中一条值得单独指出的约束是「每条假设都必须能被本轮选择的函数判定」。它把研究问题的可判定性前置到规划阶段，使写不出对应函数的猜想在进入执行前即被拒绝，而非在评估阶段以「证据不足」收场。这条约束是 EDA 循环能够收敛的关键。

**选型理由** 〔待确认〕　候选方案 A 为将研究顺序写入系统提示词，实现最简，但提示词是模型的建议而非系统的约束，长对话中易被后续指令覆盖，且无法版本化比对；候选方案 B 为在代码中硬编码流程，约束强度足够，但每次调整研究方法都需要改代码并重新分发。YAML 协议在约束强度上等同于硬编码，在可维护性上接近提示词，同时天然支持版本号与 Skill 之间的横向扩展。

**代价与边界**　协议本身成为需要维护的资产，其表达能力决定了可支持的研究方法上限。Skill 与协议双版本号带来标注成本，文档引用须分别注明，历史上已出现过版本漂移。外部 Skill 的加载能力扩大了攻击面，故限定其不能注册新函数或执行脚本。

### 3.4 支持人工审批中断与崩溃恢复

**目的**　计划执行前必须获得用户审批，审批可能持续数分钟至数小时，期间进程可能退出。流程须能在中断点精确恢复，且审批事实不能被伪造。

**方案**　由单一 `ResearchLoopGraph`（`app/research/graph/workflow.py`）承载研究过程，使用 LangGraph 的 `interrupt` 暂停于审批点，`Command(resume=...)` 携带用户操作恢复，SQLite checkpoint 保存 Graph 权威运行状态，测试场景使用内存 saver。

**机制**　Graph 以 `ingest_user → main_agent` 为入口，经条件路由分派至 `resolve_skill → eda_subagent → validate_plan → prepare_approval → approval_interrupt`，审批通过后进入 `advance_tool → mark_tool_running` 的逐函数执行循环，最终经评估路由至 `prepare_evaluation_revision`（回到 `eda_subagent`）、`prepare_need_user`（进入 `user_interrupt`）或终止节点 `persist_stop` / `persist_failure`。状态、守卫与迁移分别由 `state.py`、`guards.py`、`migrations.py` 承载，过程叙述由 `narration.py` 生成。

方案审批同时校验方案 ID、方案指纹与审批事实三者，模型意图不能绕过审批。非法 action 不改变原 checkpoint，状态保持可恢复。规划失败、函数重试与崩溃恢复与已完成评估的 Iteration 分开计数。自动修订只能在原审批范围内收缩工具、变量或滞后，扩大范围必须回到用户门禁。Graph 事件、消息与运行历史有界保存，完整桌面轨迹由会话投影保留。

**选型理由** 〔待确认〕　候选方案 A 为自研状态机加数据库持久化，控制力最强，但中断恢复、部分执行、重试计数与状态迁移的正确性需要自行验证，而这恰是易出错且难以测试的部分；候选方案 B 为不做持久化，审批超时即丢弃，实现最简但与桌面长会话的使用形态冲突。选择 LangGraph 的核心理由在于 interrupt 与 checkpoint 是其原生语义而非附加能力，人在环审批这一需求被框架直接覆盖。

**代价与边界**　流程语义与框架版本耦合，当前依赖域锁定为 `langgraph>=1.2,<1.3`，跨次版本升级须重新验证中断恢复行为。`migrations.py` 的存在说明 checkpoint 兼容性已成为实际维护项。P3 引入多折实验后，单个节点的执行时长将显著上升，须确认长任务下的 checkpoint 写入时机与桌面端的进度反馈是否仍然可用。

### 3.5 结论判定不依赖模型主观评价

**目的**　研究结论的接受与否须由证据决定，同一批证据在不同时间、不同模型版本下应得到相同判定。

**方案**　由 `app/research/evaluation/eda.py` 中的确定性评估器依据结构化工具证据给出判定，模型不直接产出最终结论，仅负责解释已判定的证据。

**机制**　评估器检查数据是否足以支持当前研究、计划中的关键证据是否已产生、假设是否得到支持或不支持或证据不足、是否存在可在原审批范围内修订的问题、是否需要补充数据或用户确认、结论是否触及方法论固有限制，并输出 `accept`、`revise`、`need_user`、`reject` 四种决策。其中 `revise` 触发原审批范围内的有限自动修订，`need_user` 回到人工门禁。

**选型理由** 〔待确认〕　候选方案 A 为由模型阅读结果并给出结论，实现最简且表达自然，但同一批证据的判定不可复现，且模型倾向于给出肯定结论，与研究场景需要的保守判定相悖；候选方案 B 为完全由用户判定，判定质量最高但丧失自动修订与循环推进能力。确定性评估器的价值在于把可规则化的判断固化，把不可规则化的判断显式交还用户，即 `need_user` 这一态的存在意义。

**代价与边界**　评估规则的覆盖度决定了自动推进的比例，规则之外的情形一律退化为 `need_user`。当前评估器为单文件实现，规则集中于一处；如果未来引入新的研究领域，继续扩充单文件还是按域拆分评估器，必须先形成架构决策，不能让其他领域语义直接混入 EDA 判据。

### 3.6 全链路溯源与防陈旧执行

**目的**　任一结论须可回溯至确定的输入、代码与参数，且方案审批之后输入发生变化时，系统须拒绝继续执行而非产出不一致的结果。

**方案**　对输入文件计算 SHA-256 指纹，对计划、Skill、协议、工具分别记录版本，对工具结果记录输出哈希，并在研究包 manifest 中汇总输入输出哈希、Git 版本与运行环境。

**机制**　数据层（`app/research/data/`）实现时间戳解析、时区统一、数值转换、非法记录识别（`loader.py`）、统一时间网格与目标外生变量对齐（`alignment.py`）、覆盖率与可获得性风险检查（`quality.py`）、对齐快照（`snapshot.py`）与字段推断（`inference.py`），输出对齐后的标准分析帧供规划、执行与评估复用。方案生成后文件被原地修改时，指纹校验失败并拒绝执行旧方案。`call_id` 与 `work_id` 配合数据指纹与输出哈希，实现执行溯源与确定性结果复用。单次研究产出的研究包结构如下。

```text
agent-<timestamp>-<fingerprint>/
├── report.md                桌面内置阅读器展示的主报告
├── methods.md               本轮方法、参数、判据、边界与证据位置
├── figures/*.svg            图表源文件
├── evidence/
│   ├── data_quality.json    数据质量证据
│   ├── eda_summary.json     完整结构化分析结果
│   └── agent_evaluation.json 评估结论与反馈
├── provenance/
│   ├── conversation.json   对话记录
│   ├── research_plan.json  计划、Skill、协议、版本与参数
│   ├── execution_trace.json 函数执行时间与结果引用
│   ├── research_loop.json  循环上下文
│   └── study_context.json  自动识别的数据与时间轴上下文
├── data/aligned_data.parquet 固定的对齐数据快照
└── manifest.json            输入输出哈希、Git 与运行环境
```

**选型理由** 〔待确认〕　候选方案 A 为仅记录报告与结果，存储成本最低，但结论无法重放，审计时只能相信报告；候选方案 B 为完整保存原始输入副本，可重放性最高但存储代价与数据合规风险显著。指纹加对齐快照的组合在可重放性与存储成本之间取得平衡，快照保证分析帧可复现，指纹保证原始输入的变更可被检出。

**代价与边界**　研究包体积随研究轮次线性增长，需要清理策略 〔待确认〕。指纹只能检出变更，不能恢复原始数据，故对齐快照是必需项而非冗余项。未来是否以该结构作为跨研究索引基础，需要在相应方案中单独评审。

### 4.1 新闻与电价结合（P2 方案草案）

- 新闻发布时间、系统取得时间、事件发生时间等时间语义，以及缺失或不确定时间的处理；

草案中的组件和字段是待验证候选；评审和测试出口满足前，不得写成已采用的生产行为。

### 4.2 电价预测实验（P3 未来研究）

## 5. 技术演进原则

后续扩展应继续遵循以下 P1 已建立的原则：

1. **模型负责方向，代码负责事实**：模型做意图、函数选择、计划修订与语言解释；可验证计算和判定由受控代码完成。未来若存在非确定性步骤，必须在新方案中说明隔离和验收边界。
2. **LangGraph 负责运行时，不负责业务算法**：Graph 保存状态与编排流程，领域数据和算法放在独立模块中。
3. **所有可执行能力必须注册和授权**：新增能力先定义契约、版本、权限、结果身份和测试，再暴露给模型；不能用提示词替代门禁。
4. **审批边界优先于自动化**：任何扩大工具、变量、数据范围或计算预算的行为都必须回到用户门禁。
5. **结果必须可复现**：输入、配置、计划、Skill 与协议版本、工具版本、代码版本、运行环境和输出哈希共同构成证据链。
6. **失败是研究结果的一部分**：数据不足、泄漏风险、无显著关系、不稳定和未完成都需要被保存，而不是只保留成功结论。
7. **当前事实与未来方案分离**：先完成并验收 P1；后续主题分别立项研究，不在 P1 技术文档中维护开发路线。
