# P2 长文本新闻抽取三方案评估与选型

**日期：** 2026-09-09  
**状态：** Final（限本文定义的评测范围）  
**受众：** P2 技术评审、项目负责人、后续维护者

## 结论

P2 MVP 选择 **方案一：全文上下文模型路由**，对应分支 `codex/p2-full-context`。

三套方案都通过了证据完整性和价格分析隔离门禁；全文方案在真实模型重复测试中取得最高的严格用例通过数（平均 5.5/6），同时模型调用最少（每轮 6 次）、估算输入 token 最低（每轮 20,829）。它的主要限制也最容易定义和审计：只有整篇文档能够连同 Prompt、结构化 Schema、输出预留和安全余量一起装入已配置模型窗口时才处理，否则整篇隔离，不静默截断。

该结论不是“已经具备生产准入”的声明。当前功能语料是 6 个针对长上下文风险设计的合成用例，真实端点每套仅重复 2 轮；上线前仍需在真实新闻保留集和实际长度分布上执行独立门禁。

## 问题与决策边界

本次比较回答：在不混合底层逻辑的前提下，哪一种长文本处理架构最适合作为 P2 MVP 的默认实现。

三套互斥方案分别是：

1. **全文上下文模型路由**：先对完整请求做 token 预算检查，按路由顺序选择能够容纳全文的模型；任何路由都无法容纳时整篇隔离。
2. **语义分块、独立抽取、全局合并**：沿自然边界切分并保留重叠区，每块独立抽取，随后按全局原文偏移去重、处理更正与冲突；任一分块失败时保留覆盖记录，但所有候选退出价格分析。
3. **顺序读取、结构化状态**：按原文顺序读取非重叠片段，通过 `upsert`、`correct`、`withdraw` 更新版本化事件状态，持久化 checkpoint 并支持失败后恢复；覆盖不完整时所有候选退出价格分析。

三方案共同继承同一安全基线：完整请求预算包含系统提示、新闻正文、结构化 Schema、输出预留和安全余量；检测模型/SDK 的输出截断信号；保存原文字符范围和覆盖状态；任何不完整覆盖均设置 `analysis_eligibility=needs_coverage_review`，不能生成价格窗口。

评测结束后已按 SHA-256 复核三分支的安全基线、功能 benchmark、统一语料和价格准入集成测试文件完全一致，避免因测试代码或语料漂移造成不公平比较。

## 评测数据与口径

### 功能语料

统一语料位于 `tests/fixtures/news_long_context/gold_cases.yaml`，共 6 个用例：

| 用例 | 风险形态 | 期望 |
|---|---|---|
| LC01 | 短新闻单事件 | 正确抽取并可进入价格分析 |
| LC02 | 事件位于长文尾部 | 不因上下文边界丢失 |
| LC03 | 同文两个事件 | 两个事件分别保留 |
| LC04 | 后文更正容量 | 只保留更正后的 300 MW |
| LC05 | 中间范围模型调用失败 | 覆盖不完整，价格准入为 0 |
| LC06 | 资产与时间/容量跨段 | 正确关联为一个事件，不能遗漏或重复 |

严格通过条件如下：

- 对 `complete` 用例，事件类型按**多重集完全相等**，不能只满足召回；容量集合完全相等；原文覆盖必须完整。
- 对 `safe_failure` 用例，不要求丢弃已验证候选，但不得有任何候选取得价格分析资格。
- 所有证据片段必须按字符偏移精确回指当前新闻版本原文。

### 运行环境

- Python 测试环境：项目 `.venv`；完整依赖包含 PySide6、statsmodels、pytest 8.4.2。
- 真实模型配置：`custom` provider、Chat API、`prompt_json` 结构化输出、`vertexai:gemini-3.8-flash`。
- 真实模型最大输出：4,096 token；安全余量：1,024 token。
- 功能基准显式使用 30,000 token 上下文预算。
- 真实端点每套方案独立运行 2 轮，每轮 6 个用例，`unit_tokens=800`。

API Key 和服务地址不进入报告或测试产物。

详细的标准化汇总见 `docs/evaluation-data/p2-long-context-strategy-results.csv`，交付复核见 `docs/p2-long-context-strategy-qa-signoff.md`。

失败形态：

- **全文上下文**：第二轮 LC04 达到 4,096 token 输出上限。SDK 提前抛出的截断被识别为 `output_truncated`，该文档被安全隔离，没有半截 JSON 或不完整事件进入价格分析。
- **分块合并**：LC02 两轮都因局部分块失败而降级覆盖；第一轮 LC04 还出现更正处理失败。安全策略正确，但可用性低于全文方案。
- **增量状态**：LC06 两轮都产生重复事件；第二轮 LC02 丢失、LC04 容量仍为 600 MW 且覆盖失败。状态迁移对模型一致性更敏感，调用链也最长。

增量状态的原始实时 JSON 由旧版宽松 scorer 生成，旧摘要把“期望事件都出现但还有额外事件”的 LC06 判为通过。本文从原始 case 明细按当前严格规则重新计分，将两轮的 6、4 修正为 5、3；当前 benchmark 源码已要求事件多重集完全相等。原始明细没有被改写。

## 设计取舍与选型理由

选型按“安全门禁优先、通过后再比较正确性、稳定性、资源和复杂度”的顺序进行，而不是把安全问题折算为可被其他分数抵消的权重。

1. **安全门禁：三者均通过。** 所有真实模型运行的证据完整性均为 100%，LC05 等覆盖不完整场景的不安全价格准入均为 0。
2. **正确性：全文方案最好。** 它取得最高的真实模型严格平均通过数，并避免分块后的跨段拼接和增量状态漂移。
3. **资源：全文方案最好。** 每个文档一次模型调用；实测调用数和输入 token 均最低。
4. **可解释性：全文方案的失败边界最清楚。** “完整请求能容纳才调用，否则整篇隔离”可以在调用前确定；分块和状态方案还需要解释局部失败、跨块冲突、修订顺序和重复归并。
5. **扩展性代价：全文方案受模型窗口限制。** 它不会处理超过所有已配置路由容量的文档。这个限制对 MVP 是可接受的，因为隔离是显式、可复核的；如果真实新闻长度分布证明隔离率不可接受，再以分块方案作为独立后续实验，而不是悄悄在 MVP 内混入第二套语义。

## 准入决定

**选择 `codex/p2-full-context` 作为 P2 MVP 长文本处理方案。**

进入下一阶段前必须满足：

1. 在部署配置中为每个路由显式设置正数 `llm_context_window_tokens`；当前本地 `.env` 的值为 0，本次功能基准使用的是显式 30,000 token 测试预算，不能把该测试参数误当成部署配置。
2. 用真实新闻保留集验证全文长度分布、隔离率、输出 token 分布和单篇多事件上限；不得只复用本次 6 个合成用例。
3. 将 `output_truncated`、`no_route_fits`、`needs_coverage_review` 纳入监控，并保持价格分析失败关闭。
4. 对 LC04 类型的长输出进行专项复测；是否提高最大输出 token，应依据真实输出分布和成本评估决定，不能仅因一次截断直接放宽。

方案二和方案三保留为实验分支，不合并进选中方案。方案二适用于未来确认“超长文隔离率不可接受、且可以承担合并复杂度”的场景；方案三更适合需要逐段恢复和显式修订历史的超长文档流，但当前不满足默认方案的正确性和稳定性要求。

## 假设与限制

| 假设 | 置信度 | 假设错误的影响 |
|---|---|---|
| P2 常规新闻大多可由至少一个配置路由完整容纳 | 中 | 隔离率上升，需要重新评估分块方案 |
| 6 个功能用例覆盖了主要的上下文边界风险形态 | 中 | 可能高估真实新闻正确率与稳定性 |
| 估算 token 能保守覆盖目标端点的实际计数差异 | 中 | 可能在边界处误放行或过度隔离 |
| 两轮真实模型重复足以支持 MVP 方案排序 | 低至中 | 排序可能随更多重复或模型版本变化 |

本评测不能证明新闻与电价之间的因果关系，也不评估价格预测能力。它只评价“新闻转成可复核事件证据，并安全决定是否允许进入价格分析”的长上下文处理部分。
