# P2 长文本新闻抽取三方案评估与选型

**日期：** 2026-09-09  
**状态：** Final（限本文定义的评测范围）  
**受众：** P2 技术评审、项目负责人、后续维护者

## 结论

P2 MVP 选择 **方案一：全文上下文模型路由**，对应分支 `codex/p2-full-context`。

三套方案都通过安全门禁：真实模型两轮测试的原文证据有效率均为 100%，不完整、撤回或取消结果错误进入价格分析的次数均为 0。在通过安全门禁后，全文方案取得最高的严格功能通过数（平均 8.5/10），并具有最低的模型调用数、估算输入 token、平均延迟、P95 延迟和实现复杂度。

全文方案不是“永远不需要分块”。它把 MVP 的失败边界定义得最清楚：完整请求能够连同 Prompt、结构化 Schema、输出预留和安全余量一起放入某个已配置路由时才调用；所有路由均无法容纳时整篇隔离，不静默裁剪。只有当真实新闻长度分布证明这种显式隔离率不可接受时，才应重新启动分块方案实验。

该结论不代表生产准入。功能语料是 10 个针对长上下文风险设计的合成用例，真实模型每套仅重复 2 轮；输出 token 用量和货币成本也因当前网关不返回可靠 usage 而不可用。

## 决策问题与三套互斥方案

本次比较回答：在不混合底层逻辑的前提下，哪一种长文本处理架构最适合作为 P2 MVP 的默认实现。

1. **全文上下文模型路由**：构造完整请求，做完整 token 预算检查，选择能够容纳全文的模型，一次抽取并做确定性校验；无路由可容纳时整篇隔离。
2. **语义分块、独立抽取、全局合并**：沿段落/句子边界切分并保留重叠，各块独立抽取，再按全局原文偏移处理重复、冲突、更正和撤回；任一块失败时整篇退出价格分析。
3. **顺序读取、结构化状态**：按原文顺序读取非重叠片段，模型只提出 `upsert`、`correct`、`withdraw` 操作，本地验证后追加不可变 revision，并用 checkpoint 支持失败恢复。

三方案共同继承同一安全基线：

- 预算包含系统提示、新闻正文、结构化 Schema、输出预留和安全余量；
- 检测 provider finish reason、SDK 提前抛出的输出截断和可重试的瞬时端点失败；
- 保存文档版本、原文字符范围、处理范围和失败范围；
- 覆盖不完整时设置 `analysis_eligibility=needs_coverage_review`；
- 取消事件留在事件台账供审计，但不生成价格窗口；
- 配置、认证和协议整体不可用仍停止全局处理，不伪装成单篇失败。

## 评测语料和严格判分

统一语料位于 `tests/fixtures/news_long_context/gold_cases.yaml`：

| 用例 | 风险形态 | 核心期望 |
|---|---|---|
| LC01 | 短新闻单事件 | 抽取停机、600 MW 和精确时间 |
| LC02 | 事件位于长文尾部 | 尾部事件不被静默遗漏 |
| LC03 | 同文停运与恢复 | 两个事件分别保留，不重复归因 |
| LC04 | 后文更正容量 | 最终只保留 `corrected`、300 MW |
| LC05 | 中间调用失败 | 允许保留候选，但价格准入必须为 0 |
| LC06 | 资产与时间/容量跨段 | 合并为一个 200 MW 停机事件 |
| LC07 | 后文撤回停运 | 保留 `cancelled` 和历史 600 MW，价格准入为 0 |
| LC08 | 中文、英文、数字、符号及时间靠近边界 | 原文不损坏，事件和 100 MW 完整 |
| LC09 | 输出达到最大 token | 标记 `model_output_truncated`，价格准入为 0 |
| LC10 | 完整请求超过上下文 | 标记 `context_limit_exceeded`，不得调用模型或裁剪正文 |

同一 benchmark 还用一个完整结构化请求验证三种阈值关系：在 4,096 输出预留和 1,024 安全余量下，该请求总需求为 7,933 token；需求小于窗口时接受、等于窗口时接受、大于窗口 1 token 时拒绝。三分支均通过。

`strict-v2` 判分规则：

- `complete` 用例的事件类型和状态都必须按**多重集完全相等**，额外事件同样判错；
- 容量集合、全文覆盖状态和预期价格准入数必须完全相等；
- `safe_failure` 用例不得有任何候选取得价格分析资格；
- 每个证据片段必须按字符偏移精确回指当前新闻版本原文；
- 用例风险描述只用于评测，不作为新闻标题发送给模型；模型只看到中性样本编号，避免标签泄漏。

早期 6 用例结果、曾把用例描述作为标题的运行、以及宽松 scorer 的运行均不参与本次选型。

## 环境与执行口径

- 项目完整 `.venv`，pytest 8.4.2；
- 真实端点：`custom` provider、Chat API、`prompt_json` 结构化输出；
- 模型标识：`vertexai:gemini-3.8-flash`；
- 最大输出 4,096 token，安全余量 1,024 token；
- benchmark 显式上下文预算 30,000 token；
- 确定性边界压力：`unit_tokens=40`；
- 真实模型重复测试：`unit_tokens=800`，每套 2 轮，每轮 10 个用例；
- 三套方案顺序运行，不并发争抢端点。

API Key 和服务地址不进入报告或测试产物。当前本地 `.env` 的 `llm_context_window_tokens=0`，因此 30,000 是功能测试参数，不是可直接沿用的部署配置。

## 单元与集成回归

| 分支 | 全量 pytest | Ruff | 价格准入集成场景 |
|---|---:|---:|---:|
| `codex/p2-full-context` | 604 passed | passed | 3 passed |
| `codex/p2-chunk-merge` | 607 passed | passed | 3 passed |
| `codex/p2-incremental-state` | 608 passed | passed | 3 passed |

三个价格准入集成场景分别验证：完整事件进入事件台账、价格窗口和证据链接；覆盖不完整的候选不进入价格窗口；撤回事件仍可审计但不进入价格窗口。

真实测试期间出现过一次 HTTP 500。共享网关原先把瞬时传输失败与全局配置失败归为同一异常，导致 benchmark 中止；现已新增 invocation-scoped transient failure，408、429、5xx、超时和连接错误按文档/步骤隔离，认证、配置和协议错误仍全局停止，并有单元测试覆盖。

分块分支提供显式且默认关闭的 `parallel_workers`。线程安全测试网关下，4 个 worker 的墙钟时间低于串行的 75%，事件结果、模型调用数和估算输入 token 完全相同。真实模型比较仍使用 1 个 worker，因为当前自定义端点的线程安全、限流和并发计费口径尚未验证；并发可能降低延迟，但不会减少 token 成本，也不会修复边界或合并错误。

增量状态分支另用 50 个已验证事件构造累计状态，在 5,000-token 上下文下确认预检在模型调用前拒绝，保留候选全部降级为 `needs_coverage_review`。注入步骤失败后的 checkpoint 恢复测试也通过，但该恢复能力是方案特性，不能抵消真实运行的串行延迟。

|---|---:|---:|---:|---:|---:|---:|---:|
| 全文上下文 | **10/10** | 1.000 | 1.000 | 1.000 | 0 | **9** | **30,644** |
| 分块合并 | 9/10 | 1.000 | 1.000 | 1.000 | 0 | 641 | 1,794,745 |

确定性测试故意用 `unit_tokens=40` 制造极端边界，调用数和 token 只用于压力路径覆盖，不是生产成本估计。分块方案的 LC07 撤回句超过该极小单元并被切散，触发 `disputed_irrelevance`；增量状态的 LC06 未形成完整跨段事件，LC07 保留为 `occurred` 而未迁移为 `cancelled`。这些失败说明两套策略对过小处理单元敏感。

## 真实模型重复功能结果

| 方案 | 两轮严格通过 | 平均通过 | 稳定用例率 | 平均调用/轮 | 平均输入 token/轮 | 平均延迟/文档 | P95 延迟/文档 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 全文上下文 | 9、8 | **8.5/10** | **0.900** | **9.0** | **30,644** | **11.98 s** | **29.87 s** |
| 分块合并 | 8、8 | 8.0/10 | 0.800 | 13.0 | 41,830 | 15.59 s | 34.02 s |
| 增量状态 | 7、8 | 7.5/10 | 0.800 | 22.0 | 41,366.5 | 24.71 s | 70.82 s |

三者每轮事件精确率均为 1.000，事件召回率分别为：全文 0.875/0.750，分块 0.875/0.750，增量状态 0.875/1.000。增量状态的事件类型召回更高，但严格通过数更低，因为 LC04 仍保留旧的 `occurred`、600 MW 状态，LC06 只有不完整事件字段；这说明事件类型召回不能替代状态、容量和覆盖门禁。

所有 6 轮真实测试的证据有效率都是 1.000，错误价格准入均为 0。

### 失败明细

- **全文上下文**：LC07 两轮均为 `model_output_truncated`；LC04 第二轮同样输出截断。全文失败时整篇隔离。
- **分块合并**：LC07 两轮均输出截断；LC08 第一轮虽抽到正确事件，但另一个块 `model_response_invalid`，因此整篇覆盖不完整并退出价格分析；LC04 第二轮输出截断。
- **增量状态**：第一轮 LC04 输出截断并停留在旧 600 MW 状态，LC06/LC08 响应无效；第二轮 LC04/LC06 响应无效。每次失败都保留最后 checkpoint，但尾段不再被当作已覆盖。

详细标准化结果见 [p2-long-context-strategy-results.csv](evaluation-data/p2-long-context-strategy-results.csv)。原始 JSON 保存在各 worktree 的 `artifacts/long-context-*-live-final3.json`，由 `.gitignore` 排除，不作为长期版本化报告。

## 成本和指标缺口

当前网关没有为每次结构化调用返回可信的 provider usage，因此以下两项标记为不可用：

- 实际输出 token；
- 按供应商价格计算的单篇货币成本。

本次只能比较保守估算的输入 token、调用次数和端到端延迟，不能据此声明精确的金额节省。生产前应扩展 `ModelGateway` 响应元数据并持久化输入/输出 usage；若经自定义代理调用，还需明确其计费模型与缓存口径。

P95 基于每套 20 个文档运行，样本量很小，仅用于当前方案相对比较，不是容量规划依据。

## 安全门槛、权重和选型理由

安全是硬门槛，不参与加权抵消：原文证据有效率必须为 1.000，错误价格准入必须为 0，完整请求边界测试必须通过，且不得出现无法检测的正文或输出截断。三套方案均通过。

通过门槛后，最终排序冻结为：严格正确性 45%、跨轮稳定性 20%、性能/成本代理 20%、工程性 15%。严格正确性使用平均严格通过率；稳定性使用稳定用例率；性能/成本代理取调用数、估算输入 token、平均延迟、P95 延迟四项“本方案最佳值/当前值”的均值；工程性以最少策略实现行数/当前行数作为维护面代理。所有子项均限制在 0–1。

| 方案 | 严格正确性 | 稳定性 | 性能/成本代理 | 工程性代理 | 加权总分 |
|---|---:|---:|---:|---:|---:|
| 全文上下文 | 0.850 | 0.900 | 1.000 | 1.000 | **0.9125** |
| 分块合并 | 0.800 | 0.800 | 0.768 | 0.413 | 0.7356 |
| 增量状态 | 0.750 | 0.800 | 0.514 | 0.341 | 0.6514 |

金额成本和输出 token 不可用，因此性能/成本项只使用已观测代理，报告不把该总分解释为生产 ROI。供应商兼容性没有单独量化：三者都使用同一 `ModelGateway`；全文方案额外要求可靠的模型窗口元数据，分块并发额外要求线程安全和限流信息，增量方案要求稳定遵循操作 Schema。

1. **安全：三者均通过。** 覆盖失败、输出截断、上下文超限和取消事件都没有进入价格分析。
2. **严格正确性：全文最高。** 真实模型平均 8.5/10，高于分块 8.0 和增量状态 7.5。
3. **稳定性：全文最高。** 稳定用例率 0.9，其余两套为 0.8。
4. **性能：全文最好。** 平均 9 次调用/轮、11.98 秒/文档、P95 29.87 秒，三项均最低。
5. **维护性：全文最简单。** 策略实现 167 行；分块和状态分别为 404、490 行，还承担跨块冲突或状态迁移语义。
6. **限制可审计。** 全文超限时明确 `context_limit_exceeded`，不会以难以发现的尾部遗漏换取表面召回。

因此选择 `codex/p2-full-context`。方案二和方案三保留为实验分支，不合并进默认方案。

## 生产前门禁

1. 为每个全文路由显式配置正数 `llm_context_window_tokens`，并验证实际端点和模型声明一致。
2. 在真实新闻保留集上测量文档长度分布、无路由可容纳率、输出截断率、严格字段准确率和取消/更正表现。
3. 针对 LC04/LC07 的 4,096-token 输出截断做专项测试；是否增加输出预算或更换原生结构化输出端点，必须以真实输出分布决定。
4. 将 `model_output_truncated`、`model_unavailable`、`model_response_invalid`、`context_limit_exceeded` 和 `needs_coverage_review` 纳入监控。
5. 扩展网关 usage 元数据后再做真实输出 token 和货币成本比较。
6. 只有真实保留集也满足 0 编造事实进入台账、0 不完整结果进入价格分析，才可讨论生产准入。

## 假设与限制

| 假设 | 置信度 | 假设错误的影响 |
|---|---|---|
| 常规 P2 新闻大多可由至少一个路由完整容纳 | 中 | 全文方案隔离率上升，需要重开分块实验 |
| 10 个合成用例覆盖主要长上下文风险形态 | 中 | 可能高估真实新闻正确率和稳定性 |
| 保守 token 估算加安全余量能覆盖代理 tokenizer 差异 | 中 | 边界处可能误放行或过度隔离 |
| 两轮真实模型运行足以支持 MVP 排序 | 低至中 | 更多重复或模型版本变化可能改变小幅差距 |

本评测不判断新闻对电价的因果影响，也不评估价格预测能力。它只评价“把新闻转成可复核事件证据，并安全决定是否允许进入价格分析”的长上下文处理环节。

