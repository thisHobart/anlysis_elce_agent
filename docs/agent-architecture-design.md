## 1. 介绍与目标（Introduction and Goals）

### 1.1 系统定位

电价研究 Agent 是一个面向电价研究人员的本地桌面研究工作台。用户以自然语言提出问题，选择目标电价和可选外生变量文件，Agent 结合数据画像提出可编辑的研究方案；用户确认后，系统按版本化研究协议调用白名单内的确定性统计函数，评估结构化证据，并生成可复核的研究报告。

系统当前的主要产出不是一条由模型猜出的结论，而是一份带有以下内容的研究包：

- 当前研究问题和可验证的假设；
- 使用的 Skill、研究协议、函数和参数；
- 数据对齐结果、质量问题和输入指纹；
- 每个函数的结构化结果、执行身份、版本、耗时和输出哈希；
- 评估器的检查项、假设状态、限制和后续建议；
- HTML/Markdown 报告、内联 SVG 图表和机器可读证据。

长期目标是把同一套受约束的研究骨架扩展到新闻事件研究和电价预测实验，但不在当前 P1 中提前宣称这些能力已经可用。

### 1.2 业务目标

| ID | 目标 | 成功表现 |
|---|---|---|
| G-01 | 降低电价研究的分析门槛 | 用户可以用自然语言描述研究问题，不必编写统计代码 |
| G-02 | 形成可信的 EDA 证据 | 数据质量、电价结构、驱动变量质量和关系证据都有明确来源 |
| G-03 | 保持人工控制 | 任何将要执行的研究方案先展示并等待用户确认 |
| G-04 | 避免方法误用 | 目标变量、外生变量、预测可获得性和描述性证据具有明确边界 |
| G-05 | 支持后续开发 | 新函数、新 Skill 和后续阶段可以复用既有契约、权限、状态和报告结构 |

### 1.3 主要利益相关者

| 角色 | 关心的问题 | 需要从架构得到的保证 |
|---|---|---|
| 电价研究人员 | 数据是否可用、哪些因素值得继续研究 | 方案可理解、证据可解释、限制不被隐藏 |
| 业务分析人员 | 研究结果是否能支撑下一步决策 | 结果与数据质量、时间范围和可获得性绑定 |
| Agent/模型集成开发者 | 模型如何获取上下文和提出动作 | 结构化契约、受限工具集和明确失败语义 |
| 统计函数开发者 | 新方法如何加入系统 | 注册、版本、参数、结果键、证据字段和测试规范 |
| 桌面端开发者 | 长流程如何展示和恢复 | Graph 状态权威、UI 投影可重建、事件可审计 |
| 维护者/发布者 | 依赖、升级和 EXE 如何交付 | 本地可运行、目录可写、旧会话可迁移、失败可定位 |

### 1.4 功能目标

#### P1：电价与外生变量 EDA

P1 需要形成以下闭环：

```text
输入数据
  → 数据画像与质量检查
  → 主 Agent 路由
  → EDA Subagent 提议方案
  → 计划校验与用户审批
  → 原子函数执行
  → 结果校验与确定性评估
  → 研究包与结果追问
```

当前内置的两个 Skill 为：

| Skill | 版本 | 目标 |
|---|---:|---|
| `price-exogenous-eda` | `3.2.1` | 判断电价和外生变量是否具备进入预测实验的证据基础 |
| `price-forecastability-audit` | `1.2.1` | 仅根据目标电价判断序列自身的结构、难度和朴素基线 |

P1 目前包含 30 个原子研究函数，覆盖数据质量、电价结构、外生变量质量、关系证据和可预测性准备度。

#### P2：新闻与电价结合（方案草案待评审）

P2 已形成 [新闻事件与电价分析技术方案草案](./phase2-news-price-analysis-proposal.md)：新闻采集由外部 API 负责，当前 `app/research/news/` 已用冻结合成新闻实现规范化和明显事件抽取。该原型拥有独立契约并由 import-boundary 测试禁止依赖 P1 EDA 领域模块；它尚未接入当前 Graph、桌面流程或电价分析。

#### P3：预测实验（未来研究主题）

P3 不在当前范围。未来若进入预测实验，必须重新评审时间顺序、特征可获得性、样本外比较、随机性、预算和测试集治理；P1 的全样本朴素基线不能直接作为样本外预测证明。

### 1.5 质量目标及优先级

发生冲突时，当前架构按以下顺序取舍：

| 优先级 | 质量目标 | 架构含义 |
|---:|---|---|
| 1 | 可复现性 | 同一输入、计划、函数版本和参数应得到可比较的结果哈希 |
| 2 | 可审计性 | 结论可以回溯到数据、计划、调用、结果和评估记录 |
| 3 | 防泄漏与防误用 | 数据角色、可获得时间、时间切分和证据语义由代码强制约束 |
| 4 | 人工可控性 | 方案执行、扩大授权和有争议的限制需要用户决定 |
| 5 | 可维护性 | Agent、流程、统计和界面职责分离，新增能力有固定接入点 |
| 6 | 交互效率 | 在不牺牲前述目标的前提下减少重复计算和无意义等待 |

### 1.6 架构范围

本文描述以下范围：桌面端入口、Agent 角色、模型网关、Skill 与研究协议、规划和权限、数据与工具、LangGraph 运行循环、持久化、报告和后续扩展边界。模型供应商的具体商业选择、新闻来源许可和预测模型的最终名单属于未决事项，不在本版架构中定死。

## 2. 架构约束（Architecture Constraints）

### 2.1 技术约束

| 约束 | 说明 | 对架构的影响 |
|---|---|---|
| Python 3.11+ | 当前实现语言和运行环境 | 领域函数、Graph、桌面端共享同一运行时 |
| PySide6 桌面端 | 主要产品形态 | 以本地三栏连续会话替代 Web 服务入口 |
| LangGraph | 当前工作流运行时 | 状态、节点、循环、中断和恢复必须显式建模 |
| SQLite checkpoint | 单机持久化要求 | 不依赖独立数据库服务，Graph 状态可以跨重启恢复 |
| OpenAI 兼容模型接口 | 模型由外部端点提供 | 需要统一网关、结构化输出和故障处理 |
| CSV/Parquet | 用户主要输入格式 | 数据层需处理时间列、数值列、频率和可获得性字段 |
| CPU 优先 | 桌面机器无统一 GPU | 当前统计函数必须在 CPU 上完成；未来算力边界另行评审 |
| Windows EXE | 交付要求 | 源码路径和打包路径不能依赖安装目录可写 |

### 2.2 产品与数据约束

- 输入数据是用户私有的目标电价、实际外生变量和预测外生变量文件。
- 原始 CSV/Parquet 由本地数据层读取和计算，不允许模型直接读取文件路径、拼接 SQL 或运行任意脚本。
- 配置的 LLM 端点是外部处理边界。模型请求只应发送完成路由、规划或解释所需的结构化画像、协议上下文和压缩证据；是否允许这些摘要离开本机由部署者根据端点和数据合规要求确认。
- 电价负值、尖峰和价格上限附近值是可能的业务现象，不得被通用异常处理静默删除或截尾。
- 时区、夏令时、市场产品、预测起点、预测范围和可获得时间不能用行号或默认常识替代。
- 相关性、互信息、Granger 前置性和分组差异只能作为描述性或样本内证据，不能自动升级为因果结论。

### 2.3 运行和组织约束

| 约束 | 说明 |
|---|---|
| 单机优先 | 当前不承担多用户并发、远程调度和集中式数据服务 |
| 数据可见性最小化 | 原始数据留在本地；发送给模型的上下文须有界并经过压缩 |
| 失败显式化 | 配置、规划、工具、评估和报告失败都必须进入可观察状态 |
| 研究过程可恢复 | 审批等待、函数执行和结果交互不能只存在于 UI 内存 |
| 代码优先于提示词 | 重要权限和业务不变式必须落到契约、编译器和评估器 |
| 小步演进 | 未来能力默认复用 P1 骨架；若需第二套流程，必须先形成新的架构决策 |

### 2.4 开发约定

- 用 Pydantic 模型表达跨边界契约，使用 `extra="forbid"` 拒绝未声明字段。
- 工具、Skill、协议和提示词都要带可追踪的版本或版本化标识。
- 任何对模型开放的能力必须先注册、授权、编译和测试。
- 任何自动修订只能在明确的 `AuthorizationEnvelope` 内收缩执行范围。
- 结构化状态由 Graph checkpoint 保存；桌面会话记录只作为投影和用户体验数据。
- 新增逻辑必须同时考虑正常流程、失败流程、恢复流程和旧状态迁移。

## 3. 上下文与范围（Context and Scope）

### 3.1 业务上下文

```text
┌──────────────────────┐
│ 研究人员/业务分析人员  │
└──────────┬───────────┘
           │ 问题、文件、审批、追问
           ▼
┌──────────────────────────────────────┐
│ 电价研究 Agent                        │
│ 研究方案、确定性分析、评估、报告        │
└───────┬───────────────┬──────────────┘
        │               │
        │结构化上下文    │本地研究包/审计记录
        ▼               ▼
┌──────────────┐  ┌────────────────────┐
│ 配置的 LLM 端点│  │ 本地文件系统         │
│ 路由/规划/解释 │  │ 数据、checkpoint、报告│
└──────────────┘  └────────────────────┘
```

| 交互方 | 输入到 Agent | Agent 输出 |
|---|---|---|
| 研究人员/业务分析人员 | 研究问题、数据文件、配置、确认/修改/停止/追问 | 方案卡、过程卡、结果卡、报告和限制 |
| 配置的 LLM 端点 | 结构化对话上下文、Skill、协议、函数 schema、压缩证据 | `DialogueDecision`、计划草案、文字解释或 Function Call |
| 本地文件系统 | CSV/Parquet、YAML、`.env`、旧会话和 checkpoint | 研究包、SQLite、桌面会话投影和备份 |
| 外部 API 已采集新闻（P2 草案） | 采集在系统外；样例契约和生产适配器尚未确认 | 新闻与电价研究所需的可追溯输入 |
| 未来实验历史（待研究） | 存储与索引方式尚未确定 | 样本外比较和历史约束 |

### 3.2 技术上下文

| 外部/基础设施 | 协议或边界 | 处理方式 |
|---|---|---|
| PySide6 | Qt 事件和线程模型 | UI 通过 `ResearchCoordinator` 与 Graph 交互，避免在 UI 线程运行长任务 |
| LLM 服务 | OpenAI 兼容 HTTP API | 仅由 `app/llm` 创建并管理 `ChatOpenAI`，所有模型角色共用网关 |
| 本地输入文件 | 文件系统读操作 | 数据层统一读取、解析、对齐、质量检查并生成指纹 |
| SQLite | 本地 checkpoint 存储 | LangGraph 保存权威运行状态，支持 interrupt/resume |
| Windows 文件系统 | 源码、EXE、用户目录 | 研究输出和内部状态写入用户可写目录，不写安装目录或临时解包目录 |
| 外部 Skill 目录 | 本地目录发现 | 只加载 `SKILL.md` 和声明的研究协议，不自动执行其脚本 |

### 3.4 输入角色

输入角色具有不同语义，不能仅因为列名相似就互换：

| 角色 | 说明 | 架构约束 |
|---|---|---|
| 研究配置 | 市场、时区、频率、列名、单位、时间范围和分析参数 | 可以由 YAML 或桌面运行时构建 `StudyConfig` |
| 目标电价 | 被解释、比较或预测的目标序列 | 执行 EDA 时必需，不能作为外生变量传入 |

| 预测外生变量 | 带预测发布时间/可获得时间的未来信息 | 可获得性未确认时只能形成限制或风险提示 |
| 新闻语料（P2 草案） | 外部 API 已采集的非规则文本来源；当前测试使用冻结合成语料 | 需要独立的数据契约和时间语义，不直接复用数值列路径 |

## 4. 解决策略（Solution Strategy）

### 4.1 核心架构原则

#### 原则 S-01：模型负责方向，代码负责事实

模型负责理解问题、选择 Skill、提出函数集合、修订方案和解释已经产生的证据。数据处理、统计计算、权限校验、结果验收和结论状态由本地确定性代码完成。

#### 原则 S-02：研究流程外置为版本化协议

研究顺序、函数许可、阶段退出门槛和方法论不变式写入 Skill 和研究协议 YAML。提示词可以帮助模型理解协议，但不能替代本地授权。

#### 原则 S-03：方案是执行前的明确边界

模型提议先变成结构化 `EDAPlan`，再经过编译和用户审批。审批后生成授权信封和工具队列，执行阶段只消费锁定对象。

#### 原则 S-04：确定性评估器拥有结论判定权

模型可以解释评估器已经确认的结构化证据，但不能自行把“没有证据”改写为“没有关系”，也不能用自然语言覆盖限制状态。

#### 原则 S-05：权威状态与展示状态分离

Graph checkpoint 保存运行权威；桌面会话保存用户可见的时间线投影；模型上下文只保留有界对话和必要的压缩证据。

#### 原则 S-06：自动化只能收缩授权范围

评估器可以触发在原审批范围内的有限修订，例如减少变量、缩短滞后或移除问题函数；新增函数、变量、数据范围或实验预算必须重新审批。

### 4.2 质量目标到架构策略的映射

| 质量目标 | 架构策略 | 主要承载组件 |
|---|---|---|
| 可复现性 | 原子确定性函数、固定数据快照、参数化调用、输出哈希 | `data`、`tools`、`snapshot.py`、`executor.py` |
| 可审计性 | 计划、调用、结果、评估、运行事件和研究包统一留痕 | `graph`、`reporting`、`manifest.json` |
| 防泄漏 | 当前由代码校验目标/驱动角色、可获得性和滞后语义；未来样本外规则另行评审 | `compiler.py`、研究协议 |
| 人工可控性 | 审批 interrupt、审批指纹、授权信封和显式恢复动作 | `workflow.py`、`guards.py` |
| 可维护性 | Agent/Graph/数据/工具/评估分层，跨层只通过契约交互 | `app/research/*` |
| 交互效率 | 工具批处理、结果缓存、压缩上下文和可重建 UI 投影 | `work_id`、`compact_evidence`、会话投影 |
| 本地交付 | PySide6 + SQLite + PyInstaller，用户目录持久化 | `desktop`、`runtime_paths.py` |

### 4.3 当前基线与未来扩展约束

```text
P1：单域 EDA 可信闭环
  ├─ 统一 Agent/Graph/权限/溯源骨架
  ├─ 30 个确定性研究函数
  └─ 真实验收与桌面交付

未来主题（顺序和方案待研究）
  ├─ 新闻与电价结合：来源、时间语义、质量与统计问题
  └─ 预测实验：防泄漏、样本外比较、预算与测试治理
```

未来新增部件原则上应落入现有层次：如果新能力要求模型绕过计划、工具绕过注册、评估器直接调用外部服务或 UI 成为第二个状态机，应先重新评审边界。这里不确定 P2/P3 的开发顺序。

## 5. 构建块视图（Building Block View）

### 5.1 总体架构

总体架构由“桌面交互、应用协调、持久化研究循环、模型协作、确定性研究执行、评估与报告”六个主要部分组成。系统内的核心控制方向是从桌面进入应用协调层，再由 `ResearchLoopGraph` 统一编排；模型和统计执行都是 Graph 调用的下游能力，不能绕过 Graph 直接修改会话或执行状态。

```text
┌────────────────────────────────────────────────────────────────────┐
│ 用户工作站                                                         │
│                                                                    │
│  ┌──────────────────┐     ┌──────────────────────┐                 │
│  │ PySide6 Desktop  │────▶│ ResearchCoordinator  │                 │
│  │ 会话/文件/方案/UI │     │ 应用事件与状态投影    │                 │
│  └──────────────────┘     └──────────┬───────────┘                 │
│                                     ▼                              │
│  ┌──────────────────────────────────────────────────────────────┐  │
│  │ ResearchLoopGraph / LangGraph                               │  │
│  │ 路由 → 规划 → 计划校验 → 人工审批 → 执行 → 结果校验 → 评估    │  │
│  │  ▲                                                  │          │  │
│  │  └────────────── 有界修订 / 中断恢复 / 终止 ──────────┘          │  │
│  └───────────────┬───────────────────────┬──────────────────────┘  │
│                  ▼                       ▼                         │
│  ┌────────────────────────┐  ┌──────────────────────────────────┐  │
│  │ LLM 协作层              │  │ 确定性研究执行层                  │  │
│  │ MainResearchAgent       │  │ Skill / Research Protocol          │  │
│  │ EDASubagent             │  │ Plan Compiler / Guards             │  │
│  │ Shared ModelGateway     │  │ Data / Alignment / Quality         │  │
│  └────────────┬───────────┘  │ ToolRegistry / Policy / Executor   │  │
│               │              └──────────────┬───────────────────┘  │
│               ▼                             ▼                      │
│  ┌────────────────────┐       ┌─────────────────────────────────┐  │
│  │ 配置的 OpenAI      │       │ Evaluation + Reporting            │  │
│  │ 兼容模型端点        │       │ 四态评估、研究包、报告与溯源        │  │
│  └────────────────────┘       └─────────────────────────────────┘  │
│                                                                    │
│  SQLite checkpoint：Graph 权威状态                                │
│  用户目录：输入文件、会话投影、研究包和备份                         │
└────────────────────────────────────────────────────────────────────┘
```

总体架构中的两条主路径语义不同：

| 路径 | 方向 | 作用 | 权威结果 |
|---|---|---|---|
| 控制路径 | Desktop → Coordinator → Graph → Agent/门禁/执行/评估 | 推进研究状态、处理中断、决定下一节点 | `ResearchLoopState` 与 checkpoint |
| 数据路径 | 本地文件 → Data Foundation → Tool Executor → Evaluation/Reporting | 形成数据快照、统计结果、证据和研究包 | `ToolResult`、`AgentEvaluation` 和研究包 |

模型端点只位于 LLM 协作层的外部边界。它接收经过裁剪的对话、数据画像、Skill/协议上下文和结构化证据，返回路由、计划提议或解释；它不直接读取原始数据、不直接执行统计函数，也不拥有 Graph 权威状态。

总体架构的调用约束如下：

1. 桌面层只能通过 `ResearchCoordinator` 发起研究动作和读取快照。
2. `ResearchCoordinator` 只能通过 `ResearchLoopGraph` 推进研究流程，不能成为第二个状态机。
3. Graph 可以调用模型协作、数据准备、工具执行和评估服务，但每个边界都通过结构化契约交互。
4. 工具执行前必须经过 Skill、编译器、注册表、策略和用户审批形成的逐级门禁。
5. 评估器和报告层只能消费已经校验的结构化证据，不能反向要求模型补造统计事实。
6. SQLite checkpoint 是运行状态的权威来源；桌面会话文件是可重建的展示投影。

### 5.2 一级构建块：系统整体

```text
┌──────────────────────────────────────────────────────────────┐
│ 电价研究 Agent                                               │
│                                                              │
│  交互入口：PySide6 Desktop                                   │
│  研究编排：ResearchCoordinator + ResearchLoopGraph           │
│  模型协作：MainResearchAgent + EDASubagent + ModelGateway     │
│  研究能力：Skill/Protocol + Plan Compiler + Tool Executor     │
│  研究基础：Data Loader/Alignment/Quality/Snapshot             │
│  结论产出：Evaluator + Reporting + Research Package            │
└──────────────────────────────────────────────────────────────┘
```

系统的单一业务入口是桌面工作区；桌面不直接调用模型或统计函数，而是通过应用协调层访问持久化研究循环。

### 5.3 二级构建块：容器和职责

| 构建块 | 代码位置 | 责任 | 权威数据 |
|---|---|---|---|

| Application Coordination | `app/research/application` | 组装数据准备、规划、执行和 Graph 调用 | 服务返回值，不持有跨重启权威状态 |

| Model Gateway | `app/llm` | 统一模型连接、结构化输出、Function Calling 和 thinking 防护 | 模型请求/响应边界 |

| Planning & Guards | `app/research/planning`、`graph/guards.py` | 草案编译、变量/参数检查、审批指纹和授权范围 | `EDAPlan`、`AuthorizationEnvelope` |

### 5.4 三级构建块：Agent 与模型协作

#### `MainResearchAgent`

主 Agent 面向用户回合进行路由，当前支持：

| 路由 | 作用 | 是否执行统计 |
|---|---|---:|
| `discussion` | 讨论方法或当前方案 | 否 |
| `new_plan` | 为新的研究目标准备方案 | 否 |
| `revise_plan` | 根据用户反馈形成方案修订 | 否 |
| `explain_result` | 解释已有结构化证据 | 否 |
| `execute_plan` | 识别用户明确确认执行当前方案 | 本身不执行，由 Graph 控制 |

主 Agent 输出 `DialogueDecision`，不能用一个自然语言“执行”替代 Graph 的审批状态。

#### `EDASubagent`

EDA Subagent 在当前 Skill 授权的函数集合内选择研究函数，形成 `EDAPlanDraft`，由本地编译器转换为 `EDAPlan`。它需要读取问题、数据画像、质量报告、协议上下文和反馈，但不读取原始数据文件，也不直接调用统计 handler。

#### `ModelGateway`

模型网关是唯一模型接入边界。它负责供应商无关的结构化输出、文本输出、Function Calling、超时/重试配置、端点能力降级和 thinking 内容处置。主 Agent 和 Subagent 共用同一网关，差异由提示词、schema 和职责表达，而不是两套模型连接实现。

#### 模型上下文边界

模型可接收：

- 有界对话历史；
- Skill 元数据、研究协议和允许的函数 schema；
- 目标/变量的名称、单位、数据画像和质量问题；
- 方案、反馈和压缩后的结构化证据。

模型不应接收或拥有：

- 原始文件路径的自由访问权；
- 任意 Python、SQL、Shell 或网络工具；
- 未注册函数的 schema；
- 作为权威的完整 Graph 状态或隐藏推理。

### 5.5 三级构建块：研究编排与门禁

```text
用户消息
  ↓
ingest_user / main_agent
  ↓
begin_episode / resolve_skill
  ↓
eda_subagent 或用户修订
  ↓
validate_plan / prepare_approval
  ↓
approval_interrupt
  ↓
lock_plan → AuthorizationEnvelope
  ↓
mark_tool_running → execute_tool → validate_tool_result
  ↓
advance_tool → finalize_iteration
  ↓
accept / revise / need_user / reject
```

Graph 节点按职责分为入口路由、研究启动、计划生成、门禁、工具执行、异常修复、评估分支、输出和中断处理。路由读取 `control` 等显式状态；展示用的 `phase` 不应成为隐式业务控制变量。

### 5.6 三级构建块：数据、工具、评估与报告

#### 数据构建块

`app/research/data` 负责把用户文件变成规范化的研究输入：读取 → 时间解析 → 时区统一 → 对齐 → 质量报告 → 指纹。方法需要连续序列时可以在方法内部做受限处理，并把插值或限制写入结果，不在数据层静默改变用户数据。

#### 工具构建块

工具注册表持有名称、描述、参数模型、handler、结果键、阶段、版本和证据字段。`ToolPolicy` 检查 Skill 授权，`ToolExecutor` 执行已锁定的调用并生成 `ToolResult`。执行器不评价结果好坏，也不决定 Graph 是否继续。

#### 评估构建块

评估器读取质量报告和合并后的结构化证据，检查研究议程是否完成，并返回 `accept`、`revise`、`need_user` 或 `reject`。评估结果不是模型自评，而是确定性规则和结果契约的输出。

#### 报告构建块

报告层把同一份结构化结果投影成可读报告和可复核资产。报告内容必须包含方法和限制；图表是证据展示，不得通过视觉样式隐藏样本不足、缺口、滞后定义或非因果性质。

### 5.7 构建块依赖方向

```text
Desktop
  → Application
    → Graph
      → Agent / Skill / Planning / Execution / Evaluation
        → Data / Tools / Reporting
          → Pydantic Contracts / Local Filesystem

Agent → ModelGateway → configured LLM endpoint
Graph → SQLite checkpoint
```

约束：

- UI 不反向持有 Graph 的业务判断；
- Agent 不直接依赖具体统计 handler；
- 统计函数不读取对话或修改 Graph；
- 评估器不调用模型决定状态；
- Reporting 只消费已校验的结果和运行引用；
- 只有 `app/llm` 创建模型客户端。

### 5.8 未来能力的候选落点

下表只用于后续方案评审时检查分层，不预先确定组件名称或是否必须实现。

| 未来能力 | 候选放置位置 | 必须保持的边界 |
|---|---|---|
| 新闻语料读取与身份记录 | 数据层 | 来源、许可、时间和输入指纹可追溯 |
| 文本结构化或事件识别 | Agent 协作层或数据准备层，待研究 | 非确定性输出不能直接成为统计结论 |
| 新闻/事件数据契约 | `schemas` | 时间语义、来源和复核状态必须显式表达 |
| 新闻与电价的统计分析 | 工具层与评估层 | 计算、假设检验和限制必须可复核 |
| 样本外切分与实验治理 | 数据、规划、工具和评估层，待研究 | 防止时间泄漏，预算和测试规则可审计 |

## 6. 运行时视图（Runtime View）

### 6.1 会话、Episode、Iteration 和尝试

运行时不是“一次聊天调用”，而是四层状态：

```text
Session：用户长期会话、历史和上下文
└─ Episode：一个独立研究目标，拥有独立终止状态
   └─ Iteration：一次计划 → 执行 → 校验 → 评估
      └─ Stage attempt：规划尝试或函数调用尝试
```

- 一个 Session 可以包含多个 Episode。
- 一个 Episode 的 `episode_goal` 在自动修订中保持不变。
- 只有完成执行并产生独立评估的 Iteration 才计入 `evaluated_iterations`。
- 规划失败、参数错误、瞬时函数错误和恢复重跑属于 stage attempt，不应伪装成已完成研究。

### 6.2 正常研究场景：从问题到方案

```text
用户输入问题
  ↓
Desktop 将消息交给 ResearchCoordinator
  ↓
Graph.ingest_user 保存消息并启动/更新 Episode
  ↓
MainResearchAgent 返回 new_plan
  ↓
加载 Skill，准备 StudyConfig、数据画像和质量报告
  ↓
EDASubagent 返回计划草案
  ↓
Compiler 补入 data_quality 并编译 EDAPlan
  ↓
Graph 写入 awaiting_approval
  ↓
Desktop 展示方案卡和反馈倒计时
```

该阶段不执行任何研究函数。用户可以确认、修改、拒绝或继续讨论；方案卡是门禁对象，不只是对话展示文本。

### 6.3 正常研究场景：审批后逐函数执行

```text
用户 approve / timeout_accept
  ↓
校验方案 ID、方案指纹和审批事实
  ↓
lock_plan 签发 AuthorizationEnvelope
  ↓
根据固定数据指纹生成 ToolCall 队列
  ↓
对每个 ToolCall：
  mark running → 执行 → 结果身份/版本/哈希校验
  ↓
队列耗尽
  ↓
合并证据并运行确定性评估器
  ↓
accept / revise / need_user / reject
```

审批完成后，模型不能插入未审批的函数；队列中的每个调用都有 `call_id`、`work_id` 和 `step_id`，执行时再次检查 Skill、工具版本和数据指纹。

### 6.4 结果评估和有限自动修订

```text
评估器
  ├─ accept       → explain_result → 生成报告 → result interrupt
  ├─ revise       → 结构化 FeedbackPacket → 受信封约束的方案收缩 → 下一 Iteration
  ├─ need_user    → 请求补数据/补元数据/扩大审批 → user interrupt
  └─ reject       → 保留拒绝原因和已有证据 → 用户修改或停止
```

自动修订的允许动作是删除函数、减少变量、缩短滞后或收缩分段范围。任何超出授权信封的动作都不能沿 `revise` 回路继续执行。

### 6.5 异常场景：规划、工具和最终化失败

| 失败位置 | 状态处理 | 用户可见动作 |
|---|---|---|
| 模型未配置/调用失败 | 记录 `response_error`，不生成伪方案 | 配置模型、重试或停止 |
| 计划契约失败 | 进入 `plan_error`，不创建执行队列 | 修改问题、重试规划或停止 |
| 数据指纹变化 | 拒绝陈旧方案 | 重新加载数据并生成新方案 |
| 单个工具失败 | 记录调用尝试和 `FeedbackPacket` | 重试函数、重新规划或停止 |
| 结果身份/哈希错误 | 结果不进入最终评估 | 修复/重试，不接受不可信结果 |
| 评估或报告失败 | 保留工具证据并进入持久化失败/用户中断 | 重试最终化或查看已有证据 |

### 6.6 重启恢复场景

```text
应用关闭
  ↓
SQLite checkpoint 保留 Graph 状态
  ↓
应用重启并打开会话
  ↓
读取 graph_schema_version 并执行安全迁移检查
  ↓
恢复当前 phase、interrupt、队列、记录和反馈
  ↓
已提交且校验通过的结果复用
未提交的执行尝试才允许重跑
  ↓
桌面从快照和事件重新投影界面
```

应用关闭期间不在后台继续执行。若审批已过期，重启后不能自动假设用户同意，必须显示过期状态并等待明确动作。

### 6.7 用户追问和下一轮研究

研究包完成后，用户可以：

- `result interrupt` 中要求解释已有结果；
- 追问某个变量、时间段或限制；
- 开始新的研究目标，创建新的 Episode；
- 继续使用当前会话的历史，但不能把旧结果当作新方案的自动授权。

主 Agent 解释结果时只接收压缩后的结构化证据和评估结果。没有证据的数值、因果关系或样本外增益必须明确说明缺失。

### 6.8 过程叙述和界面投影

`app/research/graph/narration.py` 把已发生的 Graph 事件翻译为中文阶段说明，例如准备、解析问题、生成方案、审批、执行函数、评估结果和生成报告。它不生成新的业务事实，也不展示模型私有思考链。

桌面端把事件投影到：

- 中间对话时间线的过程卡；
- 右侧完整研究过程面板；
- 方案卡和结果卡的状态；
- 会话历史和恢复提示。

投影可以重建，Graph 事件和 checkpoint 才是运行语义的来源。

## 7. 部署视图（Deployment View）

### 7.1 当前单机部署

```text
┌───────────────────────────────────────────────────────────┐
│ 用户 Windows 工作站                                       │
│                                                           │
│  ┌─────────────────────────────────────────────────────┐  │
│  │ PriceResearchAgent.exe / python -m app.desktop      │  │
│  │  PySide6 UI                                         │  │
│  │  ResearchCoordinator                                │  │
```

### 7.2 源码运行部署单元

源码运行需要 Python 3.11+ 和项目依赖：

```powershell
python -m venv venv
.\venv\Scripts\python.exe -m pip install -e ".[dev]"
.\venv\Scripts\python.exe -m app.desktop
```

源码目录中的 `.env` 由 `app/config.py` 读取，模型配置使用 `VPP_` 前缀：

```dotenv
VPP_LLM_BASE_URL=http://127.0.0.1:xxxx/v1
VPP_LLM_API_KEY=local-placeholder
VPP_LLM_MODEL=your-model-name
VPP_SKILL_PATHS=
```

### 7.3 Windows EXE 部署单元

```powershell
.\build_exe.bat            # 默认 onedir
.\build_exe.bat --onefile  # 单文件模式
```

PyInstaller 打包时包含内置 Skill。打包后的 `.env` 放在 EXE 同级目录，模型客户端按运行时路径加载配置。EXE 不应向 PyInstaller 临时解包目录或安装目录写研究结果。

### 7.4 可写目录和生命周期

| 数据 | 默认位置 | 环境变量覆盖 | 生命周期/权威性 |
|---|---|---|---|
| 研究包 | `Documents/PriceResearchAgent/research/` | `PRICE_RESEARCH_OUTPUT_DIRECTORY` | 用户可见，可长期归档 |
| 内部应用数据 | Windows `LOCALAPPDATA/PriceResearchAgent/` | `PRICE_RESEARCH_APP_DATA_DIRECTORY` | 应用状态和审计数据 |
| Graph checkpoint | 应用数据目录下的 SQLite 文件 | 随应用数据目录变化 | Graph 运行权威 |
| 桌面会话 | 会话 Store 所在目录 | 由 Store 路径决定 | UI/历史投影，不替代 checkpoint |
| 旧 checkpoint | 原 SQLite checkpoint | 随 checkpoint 位置变化 | 只读保留并提示新建对话，不在旧会话中迁移 |

删除桌面会话时，Graph 线程和会话投影可以删除，但已生成的研究报告文件不应被隐式删除；用户需要单独管理研究包生命周期。

### 7.5 外部边界和安全责任

本地应用负责：

- 不允许模型直接访问原始文件和任意执行环境；
- 限制发给 LLM 的上下文内容和历史长度；
- 对 API Key 使用 Secret 类型和配置文件读取；
- 在模型错误、工具错误和状态错误时 fail-closed；
- 将研究结果和内部状态写入用户可写目录。

部署者/用户负责：

- 选择可信的 LLM 端点和 API Key；
- 确认结构化研究上下文是否允许离开本机；
- 保护 `.env`、研究包和 SQLite 文件；
- 确认新闻来源的访问许可和预测数据的业务使用权限。

### 7.6 后续部署边界

未来主题默认先评估能否延续单机部署，但部署形态尚未决定。只有在明确需要多人协作、集中数据治理、统一索引或远程调度时，才另立服务化部署架构。届时必须重新评估租户隔离、密钥管理、原始数据存储、异步任务、并发 checkpoint 和权限模型，不能简单把当前桌面 Graph 暴露成 HTTP 接口。

## 8. 横切概念（Cross-cutting Concepts）

### 8.1 权威性和记忆分层

| 对象 | 载体 | 权威性 | 是否发给模型 |
|---|---|---|---:|
| Graph 运行状态 | `ResearchLoopState` + SQLite checkpoint | 最高 | 否；只投影必要片段 |
| 会话投影 | 桌面 Session Store | 展示/历史 | 否 |
| 对话历史 | 有界 `messages` | 仅作为模型上下文 | 是，受长度限制 |
| 研究包 | 报告、证据、provenance、manifest | 已完成研究的可复核记录 | 只按需压缩引用 |

任何新模块都必须先说明它读写哪一种状态，不能把“为了显示方便保存的字段”当作运行权威。

### 8.2 Agent 职责隔离

```text
意图识别       MainResearchAgent
方案提议       EDASubagent
流程控制       ResearchLoopGraph
模型接入       ModelGateway
统计计算       ToolExecutor + EDA functions
结论判定       deterministic evaluator
用户投影       ResearchCoordinator + Desktop
```

同一个模型服务可以承载多个角色，但角色契约不同。任何 Agent 都不能跳过 Graph 直接修改执行队列或结论状态。

### 8.3 Skill、协议与权限

Skill 由说明文本、版本、授权函数和研究协议构成。研究协议定义阶段顺序、目标、函数规则、不变式和停止条件；运行时权限由 `ToolPolicy` 和编译器再次检查。

权限逐层收缩：

```text
所有已注册函数
  → 当前 Skill 授权函数
    → 当前计划函数
      → 用户批准函数
        → 当前 ToolCall
```

上游任何层扩大范围都不能自动穿透下游门禁。外部 Skill 不能覆盖同名内置 Skill，也不能通过声明脚本获得执行权。

### 8.4 确定性、指纹和溯源

研究结果的可复现性由多项标识共同保证：

| 标识 | 作用 |
|---|---|
| 输入文件 SHA-256 | 识别文件内容是否变化 |
| `data_fingerprint` | 绑定研究配置和输入集合 |
| Skill/协议版本 | 识别方法规则是否变化 |
| 函数版本 | 识别统计实现是否变化 |
| 计划指纹 | 识别目标、步骤和参数是否变化 |
| `call_id` | 标识当前计划步骤的执行实例 |
| `work_id` | 复用同一数据、函数版本和参数的确定性工作 |
| `output_hash` | 校验工具输出是否被改写或错配 |
| manifest | 汇总环境、输入、输出和运行引用 |

只要输入、计划、工具版本或关键参数变化，就必须重新校验；不能因为函数名相同就执行陈旧方案。

### 8.5 数据时间和可获得性语义

时间语义是跨数据层、规划层、评估层和未来预测层的共同概念：

- 时间戳必须带有时区语义，统一时间网格不能以 DataFrame 行号代替市场时间。
- 正滞后固定解释为 `feature[t-lag]` 与 `price[t]` 的关系。
- `observed_only` 或 `unknown` 的变量即使相关性很高，也不能成为未来预测候选。
- 预测变量必须区分预测发布时间、预测覆盖的目标时点和模型可获得时间。
- P2 方案必须定义新闻、系统取得和业务事件所需的时间语义，不能让未知时间关系隐式进入分析。
- 未来预测实验必须定义训练、验证、测试和变换的时间顺序，避免信息回流。

### 8.6 错误、反馈和恢复语义

所有可预期错误尽量转换为结构化 `FeedbackPacket` 或明确的中断 payload。反馈至少应说明：

1. 错误发生在哪个阶段；
2. 哪个函数、计划、数据或版本受到影响；
3. 是否可以在当前授权内修复；
4. 用户可以采取哪些动作；
5. 已经产生的证据是否仍可复用。

错误不能通过空列表、默认参数或“分析已完成”的泛化文本掩盖。最终化失败时，已产生的工具结果必须保留。

### 8.7 幂等性、重试和预算

- Graph 节点应尽量幂等；重复恢复不能重复写入不可区分的研究结果。
- 结果已提交且校验通过时优先复用；只重跑未提交的 attempt。
- `work_id` 支持在自动修订和崩溃恢复中复用确定性结果。
- 规划、函数调用和已评估 Iteration 分开计数。
- 默认每个 Iteration 最多 3 次规划尝试，每个函数调用最多 2 次尝试，每个 Episode 最多 4 次已评估 Iteration。
- 相同规划失败、相同证据或相同议程重复出现时停止自动循环。

### 8.8 过程可观察性

过程事件至少记录阶段、状态、时间、函数、参数摘要、调用身份、结果引用、错误和终止原因。UI 只展示适合用户理解的过程说明，完整细节保留在运行记录和研究包中。

观测不等同于日志打印：

- 事件有稳定类别，便于桌面筛选；
- 事件顺序有单调 sequence，便于恢复和去重；
- 运行记录包含真实函数开始/结束时间；
- 不保存模型隐藏推理；
- 研究包中保留结果和溯源引用，而不是把所有大对象复制到 Graph 状态。

### 8.9 版本和迁移

以下对象需要独立考虑版本：

- Graph schema；
- Skill 版本；
- 研究协议版本；
- 研究函数版本；
- 计划提示词版本和结构化契约；
- 报告/研究包格式。

Graph schema 升级时先识别旧状态，再对不兼容状态做安全投影、备份和重建。旧计划如果引用不存在的 Skill 或函数版本，应进入重新规划，而不是使用“最接近”的版本强行执行。

### 8.10 报告和证据结构

报告遵循“正文可读、证据可查、方法可复现”的分层：

```text
报告正文
  → 结论、证据摘要、限制和后续建议
方法区域
  → 函数、参数、阈值、数据处理和判据
证据区域
  → 结构化结果、质量报告、评估和图表源
溯源区域
  → 对话、计划、执行轨迹、快照、版本、哈希和 manifest
```

报告生成不拥有评估权。报告只能呈现评估器已经产生的状态，不能因为排版逻辑缺少字段就自行补充结论。

### 8.11 隐私和数据最小化

原始文件的读取、对齐和统计在本地完成；模型只接收完成当前任务所需的最小结构化上下文。由于模型端点可能是远程服务，部署时必须把“结构化摘要是否可外发”作为独立的安全决策，而不能仅凭“桌面应用”标签判断为完全离线。

未来如果增加新闻或外部数据连接器，应为其单独记录：来源、许可、采集时间、原始内容指纹、发送边界和删除策略。

## 9. 架构决策（Architecture Decisions）

### 9.1 决策清单

| ID | 决策 | 状态 | 主要支持的质量目标 |
|---|---|---|---|
| ADR-001 | 采用本地 PySide6 桌面作为当前产品入口 | 已采用 | 本地交付、人工可控性 |
| ADR-002 | 模型与确定性计算分离 | 已采用 | 可复现性、防误用 |
| ADR-003 | 使用共享 ModelGateway 作为唯一模型接入边界 | 已采用 | 可维护性、故障一致性 |
| ADR-004 | 使用 Skill + 版本化研究协议表达领域流程 | 已采用 | 可审计性、防误用 |
| ADR-005 | 使用注册表、编译器、策略和授权信封形成逐级门禁 | 已采用 | 人工可控性、防越权 |
| ADR-006 | 使用 LangGraph + SQLite checkpoint 承载持久化研究循环 | 已采用 | 可恢复性、可审计性 |
| ADR-007 | 使用确定性评估器而不是模型自评决定研究状态 | 已采用 | 结论稳定性、可复核性 |
| ADR-008 | 使用数据/计划/调用/结果指纹防止陈旧执行 | 已采用 | 可复现性、防泄漏 |
| ADR-009 | 未来能力优先复用 P1 研究骨架；具体顺序与组件待研究 | 部分采用 | 可维护性、演进能力 |
| ADR-010 | 暂不引入 Web 服务和外部实验跟踪平台 | 暂定 | 单机简单性、部署成本 |

### 9.2 ADR-001：本地桌面优先

**背景**：用户主要在单机上分析私有电价文件，需要文件选择、方案审批、过程查看和报告查看。当前没有多租户、集中调度或远程协作要求。

**决策**：以 PySide6 桌面应用作为入口，使用 PyInstaller 提供 Windows EXE；研究结果和内部状态写入用户目录。

**后果**：部署不需要 Web 服务和数据库运维，适合本地隐私和人工流程；代价是并发、集中治理和远程访问能力有限。如果未来出现这些需求，需要另立服务化架构。

### 9.3 ADR-002：模型与计算分离

**背景**：模型适合自然语言理解，但模型生成的代码、参数和结论可能不稳定或不可审计。

**决策**：模型只产生路由、结构化计划、有限 Function Call 建议和证据解释；统计计算由注册的 numpy/pandas/scipy/statsmodels 函数完成。

**后果**：结果更容易重放和测试，模型能力受到注册函数覆盖范围限制；新增统计能力必须经过契约、注册和测试。

### 9.4 ADR-003：共享 ModelGateway

**背景**：主 Agent 和 Subagent 都需要调用同一类 OpenAI 兼容模型。如果每个 Agent 自己创建客户端，会产生配置、重试、thinking 控制和错误处理漂移。

**决策**：只有 `app/llm` 创建 `ChatOpenAI`；不同 Agent 通过职责、提示词和 schema 区分，调用统一网关。

**后果**：供应商替换和网关级安全策略集中；Agent 测试可以注入替身网关；单个模型端点仍可能成为所有模型角色的共同故障点。

### 9.5 ADR-004：Skill + 研究协议

**背景**：只向模型展示工具列表无法保证数据门禁、研究顺序和停止条件，提示词也不能构成安全边界。

**决策**：每个 Skill 由 `SKILL.md`、版本和 YAML 研究协议组成，协议声明函数集合、顺序、不变式和退出规则；注册表加载后由本地代码校验协议和授权函数一致。

**后果**：领域知识可版本化、评审和复用，模型提示词被削弱也不应改变权限；Skill 维护成本和版本迁移成本增加。

### 9.6 ADR-005：逐级门禁和授权信封

**背景**：方案修订和自动循环可能成为绕过用户审批的路径。

**决策**：草案经编译器、注册表、策略和用户审批后，签发 `AuthorizationEnvelope`；自动评估修订只能在信封范围内收缩。

**后果**：用户批准的执行范围可被明确检查，扩大范围会增加一次交互和延迟，但不能静默执行新能力。

### 9.7 ADR-006：LangGraph + SQLite checkpoint

**背景**：研究过程存在审批暂停、逐函数执行、失败恢复、结果追问和应用重启，不适合只用 UI 内存或线性脚本表达。

**决策**：用 LangGraph 表达节点、路由和 `interrupt/resume`，用 SQLite checkpoint 保存 Graph 权威状态，并为 schema 演进提供迁移和备份。

**后果**：恢复和状态检查有明确载体，不需要外部服务；需要维护节点幂等、状态边界和旧 checkpoint 迁移。

### 9.8 ADR-007：确定性评估器

**背景**：模型自评可能随模型版本、提示词和上下文变化，且容易将证据不足误写成否定结论。

**决策**：评估器根据结构化证据和集中判据输出四态决策，模型只解释已经判定的结果。

**后果**：结论状态稳定并可测试；开放式探索需要先转化为可由注册函数判定的假设，超出范围的问题进入限制或人工决策。

### 9.9 ADR-008：全链路指纹

**背景**：用户可能在生成方案后替换文件，工具实现可能升级，checkpoint 恢复可能重放旧调用。

**决策**：把输入、配置、Skill/协议、计划、函数、调用和输出分别纳入指纹或版本检查，结果复用使用稳定 `work_id`。

**后果**：陈旧方案和错配结果能被拒绝，研究过程更可审计；哈希计算、manifest 和迁移逻辑增加了实现复杂度。

### 9.10 ADR-009：未来能力优先复用 P1 研究骨架

**背景**：新闻与电价结合、预测实验等未来主题都可能依赖 P1 的权限、状态和溯源基础；P2 已有待评审草案，但当前 Graph、计划和数据契约仍是 EDA 专用。

**决策**：已采用的边界是“共享模型网关、权限、人工门禁、溯源、checkpoint 和报告基础设施，不另建一套互不兼容的治理平面”。未来领域不要求复用 P1 的 EDA 专用契约；P2 草案建议以独立领域契约和版本化制品保持弱耦合。Graph 的最终集成方式仍需架构评审。

**后果**：未来方案默认继承 P1 的门禁和证据口径，但可以拥有并列的领域 schema、计划、工具和评估器；如需抽取共享循环或迁移现有接口，必须显式记录兼容代价并保护 P1 回归。

### 9.11 ADR-010：暂不引入 Web 和外部实验平台

**背景**：当前是单机研究型 MVP，外部平台会带来服务依赖、部署和数据治理成本。

**决策**：当前使用桌面、SQLite 和研究包；只有在真实协作、数据治理或运行规模需求明确后，才评估服务化或外部实验平台。

**后果**：系统小而可交付，跨机器检索和集中实验治理能力有限；未来主题立项时按实际需求重新检查。

## 10. 质量要求（Quality Requirements）

### 10.1 质量树

```text
电价研究 Agent 质量
├─ 可信研究
│  ├─ 可复现
│  ├─ 可审计
│  └─ 统计语义不越界
├─ 安全控制
│  ├─ 工具和数据权限受限
│  ├─ 防陈旧和防泄漏
│  └─ 人工审批可验证
├─ 运行可靠
│  ├─ 中断可恢复
│  ├─ 错误可解释
│  └─ 重试不重复污染状态
├─ 使用体验
│  ├─ 连续对话和过程可见
│  ├─ 方案可修改
│  └─ 结果可追问、可打开、可分享
└─ 演进维护
   ├─ 模块边界清晰
   ├─ 契约和版本明确
   └─ P2/P3 可复用同一骨架
```

### 10.2 可验证质量场景

质量场景采用“刺激—环境—构件—响应—度量”的形式描述，便于后续验收与测试关联。

| ID | 质量属性 | 刺激/环境 | 构件 | 期望响应与度量 |
|---|---|---|---|---|
| QS-01 | 可复现性 | 同一文件、配置、计划和代码版本重复执行 | 数据层、工具执行器、报告层 | 结果结构与 `output_hash` 一致；差异可由运行时间等非证据字段解释 |
| QS-02 | 陈旧防护 | 用户在方案生成后修改输入文件 | 指纹校验、执行服务 | 执行被拒绝并提示重新生成方案，不在新数据上静默运行旧方案 |
| QS-03 | 权限安全 | 模型请求未授权函数或未注册参数 | 编译器、注册表、策略 | 计划在执行前失败，未调用统计 handler |
| QS-04 | 人工可控 | Graph 到达方案审批点 | approval interrupt、授权信封 | 未收到合法批准前没有工具执行；自动修订不能扩大授权 |
| QS-05 | 结果完整性 | checkpoint 恢复或缓存复用结果 | 结果校验器 | 调用身份、版本、数据指纹、结果键和哈希均重新验证 |
| QS-06 | 可靠恢复 | 应用在审批或函数执行中关闭后重启 | SQLite checkpoint、迁移、Coordinator | 恢复到可解释状态；已提交结果不重复执行，未提交 attempt 可重跑 |
| QS-07 | 失败可解释 | 模型、工具、评估或报告环节失败 | FeedbackPacket、Graph interrupt | 保存错误原因、影响范围、可选动作和已有证据引用 |
| QS-08 | 防误用 | 变量为 `observed_only` 或可获得时间未知 | Skill 协议、评估器 | 只能形成描述性/风险结论，不升级为预测候选 |
| QS-09 | 时间正确性 | 数据跨时区或夏令时切换 | Loader、Alignment、StudyConfig | 使用带时区时间轴对齐，不用行号近似市场时间 |
| QS-10 | 交互可见 | 工具耗时较长或循环发生修订 | Graph events、narration、Desktop | 用户能看到当前阶段、方法名、耗时和失败状态；不展示隐藏思考 |
| QS-11 | 数据边界 | 配置了外部 LLM 端点 | ModelGateway、上下文压缩 | 原始文件不由模型直接读取；发送的结构化上下文有界且部署者可识别 |
| QS-12 | 演进兼容 | Graph schema 或 Skill 版本升级 | Migrations、Registry、Plan compatibility | 旧状态安全迁移或明确要求重规划，不使用不兼容版本强行执行 |
| QS-13 | 报告可复核 | 研究完成或最终化重试 | Reporting、manifest | 报告包含方法、证据、限制、图表和 provenance 引用 |
| QS-14 | 防循环失控 | 规划或证据在循环中反复出现 | Budget、evidence/agenda fingerprint | 到达重复/预算条件时停止自动循环并交还用户 |

### 10.3 功能性要求

- 用户可以新建、选择、重命名和删除桌面研究会话。
- 用户可以加载目标电价、实际外生变量和预测外生变量，并在更换文件后使旧方案失效。
- 没有可执行数据时可以进行方法讨论；具备目标数据后才进入实际分析。
- 方案必须先展示、可修改并经过合法审批，才能执行函数。
- 研究过程和结果必须能在同一会话中继续追问。
- 研究包必须至少提供可读报告、结构化证据、方法说明和溯源信息。

### 10.4 性能和资源要求

当前不规定跨机器的固定毫秒级 SLA，但必须满足以下设计要求：

- UI 线程不执行长时间数据分析或模型调用；
- 研究函数逐个执行并汇报进度；
- 模型上下文和 Graph 事件有界，不能随会话无限增长；
- 确定性结果可以按 `work_id` 复用；
- 结果和快照缓存有界，并在终态释放；
- P3 候选模型必须在目标桌面 CPU/内存预算内经过实测后才能加入注册表。

### 10.5 质量要求与验收入口的对应

| 质量领域 | 主要自动化入口 | 主要真实验收入口 |
|---|---|---|
| 数据和统计 | `tests/research/test_data_layer.py`、`test_eda_analysis.py` 等 | 真实 CSV/Parquet 与代表性电价数据 |
| Agent 契约 | `test_eda_agent.py`、`test_prompt_contracts.py` | 真实模型 Function Calling 和失败响应 |
| Graph 恢复 | `test_research_loop.py`、回归测试 | 桌面关闭/重启、审批过期、结果追问 |
| 桌面交互 | `tests/desktop` | Windows GUI、文件权限和报告打开 |
| 报告产物 | `test_narration_and_report.py` | HTML 排版、SVG、打印/分享和研究包完整性 |
| 打包交付 | `scripts/validate_desktop_phase1.py` | onedir/onefile EXE 独立机器运行 |

## 11. 风险与技术债（Risks and Technical Debt）

### 11.1 当前阶段风险

| ID | 风险/技术债 | 影响 | 缓解措施 | 状态 |
|---|---|---|---|---|
| R-01 | 真实模型兼容性未等同于自动化测试通过 | 真实运行可能无法稳定返回 Function Call | 维护真实模型验收清单，覆盖 DeepSeek/兼容端点、thinking 和失败响应 | 待验收 |
| R-02 | 市场、单位、目标定义和预测时钟元数据不完整 | 关系或预测资格可能被过度解释 | 将关键元数据变成显式限制或执行前门禁 | 待完善 |
| R-03 | LLM 端点的结构化摘要保留策略不受本地程序控制 | 存在数据合规和泄露风险 | 最小化上下文，明确部署者责任，后续增加脱敏/端点策略 | 需确认 |
| R-04 | Graph schema 和会话投影演进较快 | 旧会话恢复失败或字段含义漂移 | 每次状态变更更新迁移、备份和恢复测试 | 持续治理 |
| R-05 | 函数目录和协议函数集合可能出现重复事实来源 | Skill、schema、UI 和执行器行为不一致 | 保持 catalog、协议和注册表启动时校验 | 持续治理 |
| R-06 | 30 个函数的组合和边界场景较多 | 低频错误可能只在真实数据中暴露 | 以参数边界、缺口、时区、样本量和结果哈希补充回归 | 持续治理 |
| R-07 | 当前 P1 的朴素基线是全样本参考 | 容易被误解为正式样本外预测结果 | 报告和 Skill 明确标注；未来预测方案重新定义样本外评估 | 已识别 |
| R-08 | 单机文件和 SQLite 可能损坏或被锁定 | 会话或研究包不可用 | 保留 `.bak`/checkpoint 备份，隔离损坏会话并提示恢复 | 已实现/持续验证 |

### 11.2 P2 方案待评审风险

| ID | 风险 | 影响 | P2 方案必须回答 |
|---|---|---|---|
| R-09 | 文本结构化可能依赖非确定性方法 | 产生错标、漏标或主观解释 | 如何定义质量基准、人工复核、版本和输入/输出身份 |
| R-10 | 新闻与事件时间语义不清 | 对齐错位或发生前视泄漏 | 需要哪些时间字段，来源与不确定性如何记录 |
| R-11 | 事件样本稀疏、窗口重叠或检验组合过多 | 统计功效低、假阳性高 | 研究问题、样本门槛、基线、多重比较和负结果如何定义 |
| R-12 | 外部 API 许可、版本和采集延迟语义不清晰 | 无法合法或可复现地重建语料 | 样例契约、稳定 ID、许可、采集时间、留存和删除策略是什么 |

### 11.3 P3 待研究风险

| ID | 风险 | 影响 | 架构应对 |
|---|---|---|---|
| R-13 | 随机切分或折外处理导致时间泄漏 | 样本外指标虚高 | 预测方案必须把时间顺序和折内处理变成可测试门禁 |
| R-14 | 多轮实验导致验证集过拟合 | 历史研究结果不再代表泛化能力 | 测试集独立解锁、实验预算和实验记录库 |
| R-15 | 模型随机性、版本和 CPU 资源差异 | 实验无法比较或无法在桌面完成 | 固定种子、版本入指纹、资源预算和重复实验规则 |
| R-16 | 只保存成功实验 | 历史检索产生幸存者偏差 | 实验记录库强制保存负结果、失败原因和限制 |
| R-17 | 未来实验契约与 `EDAPlan` 边界不清 | 产生两套重复的规划和校验路径 | 预测方案评审时确定复用、包含或统一抽象关系 |

### 11.4 技术债偿还顺序

建议按以下优先级偿还：

1. 先完成 P1 真实模型、真实数据、桌面重启和 EXE 验收。
2. 把市场、单位、目标定义和预测时钟的未知项变成明确状态，而不是隐含默认值。
3. 稳定 Graph schema、研究包格式和迁移测试；P2 实现前先评审独立技术方案，并用 import-boundary 测试保护 P1/P2 弱耦合。
4. 预测实验实现前确定实验契约、测试集治理和资源预算，不在模型开发后补防泄漏。
5. 只有当本地研究包和索引确实不足时，才评估外部实验跟踪或服务化部署。

## 12. 术语表（Glossary）

| 术语 | 定义 |
|---|---|
| Agent | 使用模型完成受约束研究决策或解释的角色；本项目主要包括主 Agent 和 EDA Subagent |
| MainResearchAgent | 负责用户回合路由、方案修订和已有证据解释的主 Agent |
| EDASubagent | 在当前 Skill 授权范围内选择 EDA 函数并形成计划草案的 Agent |
| ModelGateway | 统一模型供应商连接、结构化输出、Function Calling 和 thinking 防护的接口 |
| Skill | 一个领域方法包，包含说明、版本、授权函数和研究协议 |
| Research Protocol | 版本化的领域证据阶梯，定义阶段、顺序、不变式、退出门槛和停止条件 |
| Research Function | 一个确定性的领域统计过程，例如平稳性检验或相关扫描 |
| Tool | OpenAI Function Calling 的协议和执行边界，不等同于领域研究函数 |
| ToolRegistry | 研究函数的名称、schema、版本、handler 和证据元数据注册表 |
| ToolPolicy | 在运行时检查当前 Skill 是否允许调用某个工具的策略 |
| ToolCall | 一次带有 `call_id`、`work_id`、步骤、函数版本和参数的锁定调用 |
| ToolResult | 工具执行结果，包含调用身份、结果键、版本、数据指纹、耗时和输出哈希 |
| EDAPlanDraft | 模型提出的未编译、未审批的研究计划草案 |
| EDAPlan | 经过本地编译、契约校验并可交给用户审批的研究方案 |
| AuthorizationEnvelope | 记录用户批准的最大执行范围，并约束自动修订只能收缩的授权信封 |
| Session | 用户长期会话，包含连续对话、多个研究目标和历史投影 |
| Episode | Session 中一个独立研究目标，拥有自己的迭代计数和终止状态 |
| Iteration | 一个完整的计划、执行、结果校验和评估周期 |
| Stage attempt | 规划尝试或函数调用尝试，不等同于完成一个研究 Iteration |
| ResearchLoopGraph | 使用 LangGraph 实现的持久化、可中断、可恢复研究流程 |
| ResearchLoopState | Graph 在运行时保存的结构化状态集合 |
| Checkpoint | Graph 状态的持久化快照，当前以 SQLite 为主要实现 |
| Data Fingerprint | 绑定输入文件、研究配置和研究上下文的稳定摘要，用于防止陈旧执行 |
| `call_id` | 当前计划步骤一次执行实例的标识 |
| `work_id` | 同一数据、函数版本和规范化参数对应的可复用工作标识 |
| `output_hash` | 对结构化工具输出计算的哈希，用于结果完整性校验 |
| Data Profile | 在生成方案前展示的目标、变量、时间范围、覆盖和质量摘要 |
| Availability | 变量在预测起点之前是否已经可被模型获得的时间语义 |
| Deterministic Evaluator | 根据结构化证据和固定判据生成评估状态的本地组件 |
| FeedbackPacket | 结构化反馈，描述错误、限制、修订建议和作用范围 |
| Evidence | 工具实际产生并通过校验的结构化证据，不包括模型没有依据的推测 |
| Research Package | 一次研究的报告、方法、图表、证据、数据快照和 provenance 资产集合 |
| Provenance | 记录输入、计划、函数、执行、版本、结果和环境来源的溯源信息 |
| P1/P2/P3 | P1 是当前电价与外生变量 EDA；P2“新闻与电价结合”已有待评审草案；P3“预测实验”仍是未来研究主题；均不表示功能已实现或日期已确定 |
| 描述性证据 | 描述样本内结构、关系或风险的证据，不自动等于因果或样本外增益 |
| 前视/数据泄漏 | 使用预测时点之后才能获得的信息，或让评估信息回流到训练过程 |
