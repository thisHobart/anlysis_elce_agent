# P1—P2—P3 一轮流程实现与验证（2026-09-12）

## 结论

应用层已经实现有界的 `P1 初步分析 → P2 新闻分析 → P1 综合分析 → P3 三折回测与次日96点预测 → P1 反馈一次` 状态机。P3 只允许执行一次；每折共同有效点均不少于72且模型聚合 MAE 同时优于日、周朴素基线时结束，否则只做一次反馈分析后停止。执行异常单独记为 `failed`，不会伪装成预测未达标。

后续功能测试发现，最初的合成验证脚本在生成 P3 方案后直接调用应用服务，绕过了桌面确认卡。这个问题会造成“端到端通过”与实际用户审批流程不一致。现在 P3 计划由全流程状态投影到桌面确认卡，按钮和文字确认都通过同一个持久化流程入口执行；方案 ID、内容指纹、执行预算、结果和反馈均绑定到同一 flow。重复投影不重复创建卡片，终态方案不能再次执行。

受控合成案例完整跑到停止点并通过流程验收。21:53 的测试确认原先的404已经消失，但发现结构化输出选项只控制普通结构化对象，没有控制 P1 研究函数选择。随后将显式 `prompt_json` 兼容模式扩展到函数选择，并保留本地 Schema、函数白名单、计划编译和审批门禁。22:08 的真实重跑完成 P1 和 P2，最初因4篇新闻三遍抽取不一致而停在 `p2_needs_review`，没有静默进入 P3。针对该结果修复集合名归一化、事件类型契约、模糊时间比较、复核队列持久化和复核恢复后，4篇定向真实新闻达到三遍一致、0隔离；两条模糊时间事实经来源复核后仅保留为解释证据，不进入15分钟特征。

随后使用8篇冻结新闻完成了真实全流程。最终状态为 `feedback_complete`，桌面确认卡只执行一次 P3，并在 `not_evaluable` 后只执行一次 P1 反馈，后台停止。该运行还暴露出回测预检缺少基线可用性检查：真值每折有96点，但前一日同刻基线按各自知识截止只有1点。修复后的算法版本会按当前预测提前量重放历史预测起点，并在训练前要求每折日、周基线共同有效点不少于72；同一真实数据因此在方案生成阶段明确停止，不再进行无效训练。

## 实现范围

- `app/research/full_flow/` 保存全流程游标、运行血缘、P2 请求、特征处置、P3 反馈、执行与反馈预算。
- P2 通过现有新闻领域服务生成事件、证据、复核队列、价格窗口结果和数值特征；应用层交接文件为 `forecast_features.csv` 及其 manifest。
- P1 综合分析记录每个新闻特征的覆盖率、变化次数、同期/1小时/24小时滞后相关及前后半段稳定性。这些关系只用于描述；P3 会在最早回测锚点前重新选择特征。
- P3 方案记录 P1/P2 运行 ID、来源路径、完整 SHA-256、选择截止点、入选/排除字段；四个预测快照各自按 `as_of` 过滤新闻版本。
- 模型输入显式接受 `news_*` 字段。训练区间全缺失、恒定、来源缺失或时点不明的字段会被排除。
- 桌面修复了结果追问误触发新预测、文字确认清空方案、简短预测请求漏判、P1/P3 摘要混用及中断后假运行状态。会话 schema 升至18，`eda/news/forecast/feedback` 血缘进入同一会话；失去后台任务的预测恢复为待重新确认状态，并复用已保存的逐折检查点和执行预算。
- 描述统计按均值、最低值、最高值等交付项验收，不再强制把它们变成研究假设。

## 真实运行状态

真实山东数据库再次取数成功。当前 `.env` 中 `custom + chat + vertexai:gemini-3.8-flash + prompt_json` 已不再返回404；随机字段 Schema 探针1/1通过。最小原生工具探针确认代理会丢弃 `tools`，因此显式兼容模式改为同时传递函数白名单。修复后的真实运行在29.55秒内生成 P1 方案，P1确定性执行耗时0.25秒，随后用8篇冻结新闻完成398.43秒的 P2 三遍模型抽取。

初次 P2 共形成4个事件，4篇文档因三遍抽取的处置或事件内容不一致进入隔离区；质量门禁据此返回 `p2_needs_review`。1个合格短期负荷事件进入价格窗口分析，6小时和24小时窗口与预期方向一致；该新闻实际取得晚于事件发生，只能用于事后解释。流程没有执行 P1 综合或 P3，也没有写业务数据库、修改 `.env` 或修改浏览器 MCP。

修复后的定向真实复测使用这4篇新闻的 v2 版本和同一份山东价格快照。三遍结果为4个事件、0个隔离：储能集中放电稳定归类为 `storage_dispatch`，新能源机制电价与用户侧报价稳定归类为 `policy_long_horizon`，度夏移峰稳定归类为 `demand_shock`。储能和度夏事件只有模糊时间，复核状态为 `accepted + needs_time_review`；其 `count_storage_dispatch` 和 `count_demand_shock` 在15分钟特征表中的非零行均为0。复核后再次运行没有模型调用，结果为 `complete`，证明缓存、复核恢复和时点隔离同时生效。

完整真实运行复用了合格 P1 证据，8篇新闻形成8个事件、0个隔离。日期级或模糊时间事实经复核后只保留为解释证据。新闻特征语义检查发现，一次负荷峰值曾被错误当成永久活跃状态；修复后 `demand_shock` 和无结束时间的 `storage_dispatch` 只在实际事件区间计数，晚到报道只产生公告脉冲。重建 P2 和 P1 后，P1 只保留 `news_new_announcement_count`，其余活跃状态字段因无变化被排除。

P3 在桌面独立确认卡中使用默认生产训练配置执行一次，耗时871.73秒，生成2026-09-13的96点预测。真实新闻均在2026-09-12才取得，而最早回测选择截止点在2026-08-28，因此 P3 正确排除了全部新闻字段。三折真值和核心预测变量各有96点，但旧预检没有检查日朴素基线的可用性，最终三折共同有效点为1、1、1，状态为 `not_evaluable`。聚合指标只有3个共同点：模型 MAE 48.79、日朴素 MAE 49.61、周朴素 MAE 93.92；这些数值不能用于证明预测增益。流程随后生成一次 P1 反馈并停止，P3/反馈预算为1/1，桌面工作线程为空闲。

反馈后核对了历史价格的 `available_at/create_time`。以2026-08-28目标日为例，在与当前任务相同的2026-08-27 22:00预测起点，2026-08-27全天96个价格点只可见00:00一个点；其余记录在次日约10:26才成批可用。算法版本已升级到 `1.2.0+operational_backtest_origin`：历史折复现当前任务提前量，并在 P3 训练前检查日、周基线共同点。真实修复验证因只有1/96点而在方案生成阶段停止，这是数据可用性限制，不再被误报成模型表现。
