# 工具调用可调试性与准确性评测改造方案

日期：2026-09-21。状态：设计提案，尚未实现下述改造。

范围更正：本文件偏重功能与评测体系。根据后续澄清，当前优先整改抽象层、调用链与测试耦合，主方案改为[工具调用工程整改](tool-calling-engineering-refactor.md)；本文仅保留为后续参考。

## 1. 目标与现状

目标：对一次研究请求，能够明确回答模型看到了哪些工具、为什么可以调用、提出了什么调用、系统如何改写和执行、哪里失败，以及调用是否符合用户目标。

本次审阅聚焦 P1 EDA 调用链。优先覆盖现有 30 个原子研究函数和分析配方；P2 MCP 与 P3 后续接入共同的追踪接口，但分别维护领域验收标准，不以 P1 测试替代其验收。

| 当前代码 | 已有能力 | 本次需要补齐的部分 |

## 2. 工具说明：一个来源，多种展示

扩展现有 ResearchFunctionSpec/ToolSpec，不另建一份与代码手工同步的工具表。参数的类型、默认值、范围仍由现有 Pydantic 模型和受信配置定义，说明引用这些定义。

每个函数必须描述：

- 能回答的问题，适用场景，不适用场景，与易混淆工具的区别。
- 数据前提：数据角色、时间频率、可用样本、常数列、缺失值处理和所需前置证据。
- 参数：含义、单位、边界、示例、批处理语义；明确哪些由模型选择，哪些由本地配置注入，哪些来自当前审批范围。
- 输出：结构、证据字段、单位、空值与样本不足状态，能够支持和不能支持的结论。
- 执行属性：版本、读写副作用、缓存条件、重复调用规则和可重试错误。
- 至少一个正确示例、一个不该调用的反例，以及边界案例。

例如 `relationship_pearson_positive_lead_scan` 要说明正滞后对应历史外生变量与当前电价配对，`max_lag` 按数据时间步计数。小时数据的 24 步与 15 分钟数据的 24 步不是同一个时长；还应通过实现核对扫描是否包含零滞后。模型只能提交授权变量与可选参数，`min_observations` 等本地安全参数不应出现在模型示例中。结果不能直接证明因果关系或样本外预测增益。

由同一元数据生成：完整工具手册、模型可见的精简 Schema/说明、调试界面的说明卡。领域 Skill 中的调用时机规则仍保留在协议层，由统一构建器引用并检查冲突。保存说明版本、协议版本和实际 Schema 哈希，避免说明修改后无法复现旧运行。

增加目录一致性检查：函数是否全部注册；输出声明是否存在；示例是否能通过模型侧和执行侧各自的契约；配方子函数是否存在且获得授权。固定计划与动态范围的重复调用规则要分别写明，不能把固定计划的“每函数最多一次”误用于动态参数变体。

## 3. 调用过程：保留提议、编译和执行三种事实

目标链路：

```text
用户问题 + 数据快照 + 已批准范围
→ 构建模型请求，保存实际工具说明快照
→ 模型提议（原工具名、原参数、provider call ID）
→ 权限/参数/预算校验，配方展开，本地参数注入
→ 编译调用（原子函数、最终参数、变换原因）
→ 缓存核验或真实执行
→ 输出结构和语义校验
→ 按 provider call ID 回传结果
→ 下一轮选择或停止
→ 独立案例评测
```

生产流程和测试必须经过同一编译器、授权门禁、执行器和结果校验器。测试通过显式 fixture 提供审批状态，不能在生产代码里增加绕过审批的开关。

在既有 ToolCallRecord、ToolCallGroupRecord、CallEvidenceRecord 上建立统一追踪视图；新增追加式阶段事件，不维护第二套相互竞争的调用状态。至少记录：

- 会话、episode、iteration、模型轮次、provider call ID、local call ID、work ID、attempt ID，以及配方父子关系。
- 模型实际请求引用、工具 Schema 快照、模型公开输出/调用提议；不保存隐藏思考、密钥或认证头。
- `proposed_arguments`、`compiled_arguments`、字段来源及差异；本地注入与模型错误修复分开标记。
- 失败阶段、稳定错误码、可重试性、每次尝试耗时、结果摘要、完整结果引用、数据和输出哈希。
- 执行来源：system_preflight / model_direct / recipe_child，以及 real / cached / replay。缓存命中不可计为真实执行，系统预检不可计为模型选对了工具。
- 回传给模型的结果摘要引用及裁剪标记，便于排查“工具算对了，但模型没看到关键证据”。

提议被拒绝时还没有 local call ID，也必须能按模型轮次和 provider call ID 定位。provider ID 缺失或重复时使用本地提议事件 ID 诊断，不伪造有效协议身份。

错误分层：model_transport、model_protocol、authorization、arguments、compilation、execution、output_validation、tool_feedback、evaluation。沿用现有 FeedbackPacket，并逐步增加稳定分类字段。

完整事件按运行写入 JSONL 或已有持久化设施，界面展示其摘要；大对象用引用读取，避免把全部日志装进 LangGraph 状态。导出默认脱敏。会话崩溃留下 running 状态时，恢复逻辑标记中断并记录新尝试，不能把未知状态当成成功。

## 4. 调试入口与回放

先提供 CLI，稳定后将相同查询能力接入桌面研究过程面板。建议增加 `scripts/debug_tool_call.py`，提供以下明确区分的模式：

| 模式 | 输入 | 验证对象 |
|---|---|---|
| inspect | run/call ID | 原提议、编译差异、门禁、配方子调用、结果和错误链 |
| dry-run | 已批准范围、工具名、参数 | 编译和权限，不执行 handler |
| execute | 固定数据、调用参数 | 单工具真实计算和结果校验 |
| replay-execution | 已保存编译调用与数据快照 | 不调用模型，重跑确定性工具，比较证据 |
| replay-model | 原请求和已记录工具结果 | 使用相同上下文重新观察模型决策，明确计入新的模型请求 |

回放验证工具版本、数据指纹与环境；不同版本作为对比运行，不冒充原运行复现。确定性证据采用明确的数值容差比较，时间戳与运行 ID 不要求一致。涉及外部读取的工具默认使用冻结快照；重新访问远端应作为新的 live 运行。

桌面调用详情采用“模型提议 → 本地编译 → 执行结果 → 评测差异”四部分，错误直接定位到阶段、字段和原因。只展示可审计决策与证据，不展示私有思考链。

## 5. 测试：分开验证程序、模型和结果

| 层级 | 输入与执行方式 | 判定依据 |
|---|---|---|
| 工具契约测试 | 固定参数、固定数据，真实执行每个原子函数 | 独立算例/已知数学性质、输出类型、数值容差、边界状态 |
| 调用编排测试 | 预设模型回复，真实编译与执行 | 审批、权限、参数注入、配方、错误回传、缓存、重试、恢复 |
| 真实模型单轮选择测试 | 自然语言问题、固定上下文和工具集合 | 模型提议是否满足人工审阅的选择与参数约束 |
| 真实模型多轮闭环测试 | 固定数据、真实模型、真实工具、真实结果回传 | 逐轮动作、最终证据、停止行为及任务目标 |

已有测试保留。新增 `tests/fixtures/tool_calling/` 保存案例与冻结数据，新增 `app/research/evaluation/tool_calling/` 保存案例契约和评分器，新增 `scripts/benchmark_tool_calling.py` 运行业务基准。这些路径是拟新增模块。

每个案例应包含：用户问题、数据快照、已知上下文与审批状态、必要工具/证据、允许替代方案、禁止工具、参数谓词、顺序依赖、允许的最终状态、输出断言和最大调用预算。

不要要求所有问题只有唯一调用序列。以必需证据和先后依赖为核心，允许不同合法工具组合；配方展开后按原子证据比较，同时单独评估配方选择是否适当。澄清信息、请求授权、说明数据不足、无需调用也可以是正确终态。

案例示例：用户要求“用小时数据看负荷提前 1 到 24 小时与电价的关系”。在数据可用且已授权的 fixture 下，要求产生对应负荷变量的领先扫描证据，模型提出 `max_lag=24`，变量严格限定在授权集合；禁止扩展到无关变量或预测训练。模型不应提出本地管理的样本阈值，编译结果则必须包含受信值。选择与执行评分分开。

首批覆盖每个原子函数的正例、反例与参数/数据边界；另覆盖相似工具区分、无需调用、缺数据、范围越界、频率换算、重复调用、结果不足后的补充调用、配方局部失败、传输失败与恢复。无参数工具以数据边界替代参数边界。

预期结果由独立参考计算、可人工核算数据及领域审阅确定，不能让被测模型或同一 handler 生成答案再证明自己正确。开发案例与保留案例按问题模板/数据来源分离；增加对评分器的错误注入测试，证明它能抓住错工具、错变量、错时长和无用调用。

## 6. 准确性：分项评分，不以执行成功代替选对

| 指标 | 判定与分母 |
|---|---|
| 协议可用率 | 能获得可解析协议响应的模型请求 / 已尝试请求；传输和协议故障分列 |
| 工具选择 precision / recall | 对可评分提议按案例的合法方案匹配：正确动作占提议动作；必需动作或证据被覆盖的比例。允许可选工具不自动算错，超出相关集合与预算才算冗余 |
| 参数语义正确率 | 工具选择正确的提议中，变量、单位、范围和分段等全部满足约束的比例；同时报告工具与参数联合正确率，避免条件分母掩盖错工具 |
| 原始提议通过率 | 无需纠错且满足全部选择/参数约束的案例 / 可评分案例；合法的本地参数注入不算模型修复 |
| 执行与结果正确率 | 分别报告真实执行完成率，以及通过独立输出断言的比例；缓存与回放单列 |
| 任务成功率 | 满足全部必要证据、禁止项、停止条件的案例 / 可评分案例；并给出所有尝试案例中的端到端成功率 |
| 恢复与效率 | 首轮成功、反馈后成功、重试次数、无效/重复调用数、延迟；可取得真实 usage 时才报告 token/费用 |

无工具场景单独报告正确不调用率；precision/recall 的空分母标记 N/A，不能伪造 100%。基础设施故障可从条件语义准确率分母排除，但必须列出排除数量、原因和评测覆盖率；总尝试分母的端到端成功率保留这些失败。

主要判据使用确定性规则。对“最终解释是否忠于证据”等开放项，可以增加人工复核或辅助模型评审，并保存依据；辅助评审不能覆盖硬约束失败。

每次基准输出：配置/模型路由/Prompt/Schema/工具/数据版本、逐案例判定、预期与实际差异、错误分布和前后版本对比。真实模型每例建议初期重复 3–5 次观察波动，报告样本数与区间，不把少量重复当成稳定性证明。协议模式分组统计。

## 7. 落地顺序与验收

1. **工具契约与评测标准**：补齐 30 个原子函数和配方说明；统一生成模型 Schema 和手册；审阅第一批案例与评分器。验收：目录全覆盖、示例合法、错误注入能被评分器发现。
2. **最小可运行调试链路**：贯通提议、编译、执行、回传追踪，先交付 CLI 和单案例真实闭环；随后抽取工作流中重复的生命周期逻辑。验收：任何被拒绝、执行失败或配方子调用均能定位，能从冻结快照回放，既有回归测试通过。
3. **批量准确性评测与迭代**：运行开发集和保留集，按错误类别改说明、参数约束或选择提示。验收：全部案例有判定或明确不可评分原因，原始提议和系统最终表现分别报告；先建立真实基线，再约定质量阈值。
4. **桌面调试展示与领域扩展**：接入调用详情和前后版本对比，再适配 P2/P3。验收：从界面能定位案例中的错误调用，导出记录足以复核，同一追踪身份贯穿所有展示。

硬约束用例必须全部通过：越权不执行、错误结果不进入有效证据、provider 回传身份正确、缓存恢复经过校验。这些是发布门禁，不是通过率的加权加分项。

完成标准：从一个失败案例可以确定问题属于工具说明、模型选择、参数生成、本地编译、执行实现、结果回传还是评测规则；修改后可以用同一批冻结案例验证改善，并检查是否引入退化。
